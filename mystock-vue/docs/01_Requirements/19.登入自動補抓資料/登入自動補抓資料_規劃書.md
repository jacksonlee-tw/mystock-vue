## 1. 目的與範圍

### 1.1 需求來源

使用者（2026-09-28）：「登入首頁時，系統自動檢查所有爬回來的數據是否為最新的狀態，若有未更新的股票，自動啟動爬蟲程式更新。」

實際痛點：每日資料靠排程（台股 14:30、美股 06:00）抓取；**只要排程那一刻服務沒在跑**（筆電關機、容器重啟、當次抓取失敗），當天資料就會一直缺到下一次排程，而首頁上的熱力圖、警示、持股損益都會默默顯示舊資料。

### 1.2 交付範圍

| 項目 | 內容 |
|---|---|
| 新鮮度判斷 | 後端依市場算出「預期最新交易日」，逐檔比對追蹤清單個股與大盤／類股指數的最後資料日期 |
| 自動補抓 | 有落後標的且條件允許時，於背景以 `incremental` 模式只補落後標的，完成後串接策略掃描（與每日排程同一條鏈，AI 批次除外，見 ADR-05） |
| 觸發時機 | 首頁偵測到**擁有者已登入**時（頁面載入時已登入、或在首頁完成登入 `owner-auth-changed`） |
| 首頁提示 | 首頁標題列下方一條「資料狀態列」：檢查中／已是最新／更新中（進度）／仍落後（原因＋手動重試） |
| 原地刷新 | 補抓完成後首頁各卡片**保留原內容**重新抓取（硬性規則 #1），並 toast 通知 |
| 保護機制 | 伺服器端互斥＋節流（同一市場同一預期交易日只自動補抓一次）、排程時窗避讓、未登入不觸發 |

### 1.3 不在本文件範圍

| 不做 | 原因 |
|---|---|
| 全市場每日作業鏈（`market_fetcher.run_daily_pipeline()`，選股用的上千檔行情） | 量體大、打 TWSE 次數多，已有自己的續傳機制（`backfill.py` §3.9.5）；若登入就觸發，等於每次開首頁都可能發動一次重量級抓取。列為後續評估 |
| MOPS 月營收／季 EPS、總經指標、新聞、匯率 | 更新週期不是「每個交易日」，「落後」的定義不同；各有自己的排程 |
| 在首頁以外的頁面觸發 | 需求明確為「登入首頁時」；其他頁面維持現狀 |
| 修改既有 `/fetch/trigger` 未掛 `require_owner` 的問題 | 既有行為，另案處理；本功能新端點一律掛 `require_owner` |
| 完整的證交所／NYSE 行事曆 | 見 T2、ADR-04，以「已知休市日＋節流」處理 |

### 1.4 名詞定義

| 名詞 | 定義 |
|---|---|
| **預期最新交易日（expected date）** | 以「現在時間」推算，該市場**應該已經有收盤資料**的最近一個交易日 |
| **落後（stale）** | 標的最後一筆資料日期 `< expected date`，或完全沒有資料 |
| **補抓（catch-up）** | 針對落後標的的背景 `incremental` 抓取＋串接掃描，`trigger_type = "auto_catchup"` |
| **節流鍵** | `(market, expected_date)`；同一鍵只自動補抓一次（失敗例外，見 §3.4） |

## 2. 現況盤點

### 2.1 既有的補抓機制與缺口

| # | 機制 | 位置 | 缺口 |
|---|---|---|---|
| **G1** | 啟動回補 `run_startup_backfill()` | `services/backfill.py`，`main.py` lifespan | **僅 `DATA_SOURCE=postgres` 才執行**；目前本機 `.env` 是 `json`，等於完全沒有補抓。且只在服務啟動那一刻跑一次，服務長時間運作期間錯過排程不會補 |
| **G2** | 每日排程 `_scheduled_tw/_us` | `services/scheduler.py` | 只在固定時間觸發；錯過就等明天。`_run_if_idle()` 遇到有任務執行中直接跳過（含掃描），不排隊 |
| **G3** | 指數「同步」按鈕的新鮮度判斷 | `api/v1/endpoints/indices.py` `/indices/sync` + `get_latest_expected_tw_trading_date()` | 只有台股、只看類股指數、需人工按 |
| **G4** | 追蹤清單「資料缺漏」 | `StockRepository.get_coverage_summary()` | 只算區間內 `close` 為空的天數，**不判斷「最後日期是否落後」** |
| **G5** | 美股沒有「預期最新交易日」函式 | — | `markets/us.py` 只有 `session_state()`（盤前／盤中／盤後），沒有休市日資料 |

### 2.2 可直接重用的既有資產

| 資產 | 用途 |
|---|---|
| `services/index_fetcher.get_latest_expected_tw_trading_date(now)` | 台股預期最新交易日（週末＋`data/_no_trading_days.json`＋14:30 cutoff），**直接沿用**，不重寫 |
| `StockRepository.get_coverage_summary(symbols, market)` | 透過 `load_stock_data()` 取每檔 `end_date`，**尊重 DATA_SOURCE 唯一分支點**（CLAUDE.md），json／postgres 都能用 |
| `services/index_fetcher.load_index_json()`、`get_index_definitions(market)` | 指數最後日期 |
| `tracking_service.get_crawl_enabled_symbols(market)`（async） | 追蹤清單＝爬蟲範圍的唯一來源 |
| `fetch_status` 單例 | 台股／美股／指數共用的互斥旗標與進度；前端 `useCrawlerStatus()` 已在輪詢 `/fetch/status` |
| `run_fetch_process` / `run_us_fetch_process` / `run_index_fetch_process` | 皆支援 `target_stocks`/`codes`、`mode="incremental"`、`trigger_type` |
| `scheduler._publish_fetch_result()` / `_scan_after_fetch()` | 抓取後的通知事件與策略掃描鏈（掃描本身有 `(symbol, strategy, direction, trade_date)` 去重，重跑安全） |
| `config.get_schedule_config()` | 各市場排程時間／是否啟用，用於排程時窗避讓 |
| `core.owner_auth.require_owner` | 擁有者驗證 |
| 前端 `HomeView` 的 `ownerAuthenticated`、`HomeSectionCard` 的 refresh-overlay | 觸發時機與原地刷新 |

### 2.3 重要限制

- `fetch_status` 是**全行程唯一**的互斥旗標：台股、美股、指數**不能同時抓**，補抓必須在單一背景工作內**依序**處理多市場。
- 既有 `/fetch/trigger` 的「檢查 is_running → add_task」**不是原子操作**；多分頁同時開首頁會重複派工。本功能須自帶鎖（ADR-03）。
- 台股逐日抓取是「一天一個任務、整個市場一次」（MI_INDEX/MI_MARGN/T86），**補 1 檔和補 60 檔打 TWSE 的次數相同**；因此只補落後標的的主要價值在美股（yfinance 逐檔）與減少 JSON 重寫。
- `crawler_run.trigger_type` 為 `VARCHAR(20)`；`"auto_catchup"`（12 字元）可直接寫入，**不需 migration**。
- 停牌／下市個股永遠拿不到新資料 → 若不節流會「每次開首頁都補抓一次」（ADR-02）。

## 3. 設計

### 3.1 整體流程

```text
使用者開 / （或在首頁完成登入）
  └─ HomeView：ownerAuthenticated === true
       └─ useDataFreshness().ensureFresh()        ← 前端每個分頁 session 最多 10 分鐘呼叫一次
            └─ POST /api/v1/data-freshness/catch-up
                 ├─ [lock] 逐市場計算 report（expected_date、落後個股、落後指數）
                 ├─ 逐市場決定 action：up_to_date / fetch_running / schedule_window / throttled / triggered
                 ├─ 有 triggered → 登記節流鍵 → 背景 thread：依序 tw → us
                 │     每市場：指數（若落後）→ 個股（僅落後者，incremental）→ 通知事件 → 策略掃描
                 └─ 回傳 report + actions + fetch 快照
       └─ DataFreshnessBar 顯示狀態；triggered 時接 useCrawlerStatus() 進度
            └─ isRunning true → false：refreshKey++ → 各 panel 保留內容重新抓取 + toast
```

### 3.2 預期最新交易日（`services/trading_calendar.py`，新檔）

```python
def get_latest_expected_trading_date(market: str, now: datetime | None = None) -> str
```

| 市場 | 規則 |
|---|---|
| `tw` | 直接委派 `index_fetcher.get_latest_expected_tw_trading_date(now)`（14:30 Asia/Taipei cutoff、週末、`_no_trading_days.json`）。**不搬動原函式**，避免影響 `/indices/sync` |
| `us` | 以 `America/New_York` 時間：今天是平日且已過 **17:00 ET**（收盤 16:00 + 1 小時讓 yfinance 日線就緒）→ 今天；否則往前一天。再往前跳過週末與 `US_MARKET_HOLIDAYS`（模組內常數：2025–2027 NYSE 全日休市日，約 30 筆，附來源註解與「每年 12 月補下一年」提醒） |

- 回傳 `YYYY-MM-DD` 字串，與 JSON 資料的日期鍵同格式，可直接字串比較。
- 純函式、可注入 `now`，**必須有單元測試**（§8 S1）。

### 3.3 新鮮度報告（`services/freshness_service.py`，新檔）

```python
async def build_market_report(market: str, now: datetime | None = None) -> dict
```

回傳：

```jsonc
{
  "market": "tw",
  "expected_date": "2026-09-25",
  "checked_at": "2026-09-28T09:12:03+08:00",
  "stocks":  { "total": 66, "stale": [{ "symbol": "2455", "last_date": "2026-09-24" }] },
  "indices": { "total": 34, "stale": [{ "code": "TWII", "last_date": "2026-09-24" }] },
  "is_stale": true
}
```

- 個股：`get_crawl_enabled_symbols(market)` → `StockRepository().get_coverage_summary()` → `end_date is None or end_date < expected_date` 即落後。
- 指數：`get_index_definitions(market)` → 各 `load_index_json(code, market)` 的 `max(keys)`。
- **無資料的新標的**（`end_date is None`）也算落後——剛加入追蹤清單、背景抓取失敗者一併補。
- 報告在行程內快取 **60 秒**（key：market），多分頁同時開不會重複讀 60+ 個 JSON 檔。

### 3.4 補抓決策與派工

```python
async def catch_up(markets: list[str] | None, force: bool = False) -> dict
```

每個市場依序判斷，**第一個成立的條件即為該市場 action**：

| 順序 | 條件 | action | 說明 |
|---|---|---|---|
| 1 | `not report.is_stale` | `up_to_date` | — |
| 2 | `fetch_status.is_running` | `fetch_running` | 已有任務（排程／手動／另一個補抓）在跑，前端直接接進度 |
| 3 | 現在落在該市場排程時窗 `[排程時間 − 10 分, 排程時間 + 90 分]` 且排程啟用，且 `not force` | `schedule_window` | 讓排程自己跑完整鏈；避免補抓佔住 `fetch_status` 導致 `_run_if_idle()` 整個跳過（含掃描）。時窗常數放 config 預設值 |
| 4 | 節流鍵 `(market, expected_date)` 已成功補抓過，且 `not force` | `throttled` | 補過仍落後＝多半是停牌／下市／假日判斷誤差，不再每次重打。回傳仍落後清單供前端顯示 |
| 5 | 節流鍵上次補抓**失敗**且距今 < 30 分，且 `not force` | `throttled` | 失敗允許 30 分後重試 |
| 6 | 其他 | `triggered` | 登記節流鍵（狀態 `running`）→ 納入本次背景工作 |

- **原子性**：整個「算報告 → 決策 → 登記節流鍵 → 啟動 thread」包在模組層 `asyncio.Lock` 內；背景工作本身再以 `threading.Lock` 防止同時兩個補抓 worker。
- **背景工作**（`threading.Thread(daemon=True)`，比照 `market_fetcher` 手法；不用 FastAPI `BackgroundTasks` 以免多市場串接時跟請求生命週期綁在一起）依序處理 `triggered` 的市場：
  1. 每一步開跑前再檢查 `fetch_status.is_running`，被排程搶先就記 log 並將該市場節流鍵標為 `skipped`（下次可再試）。
  2. 指數有落後 → `run_index_fetch_process(market, codes=落後代號, mode="incremental", trigger_type="auto_catchup")`
  3. 個股有落後 → `run_fetch_process` / `run_us_fetch_process(target_stocks=落後代號, months=get_months_range(), mode="incremental", trigger_type="auto_catchup")`
  4. `scheduler._publish_fetch_result(market)` → `scheduler._scan_after_fetch(market, run_ai_batch=False)`（ADR-05）
  5. 依 `fetch_status.status` 將節流鍵標為 `done` / `failed`；清掉該市場報告快取。
- 節流紀錄存**行程記憶體**（dict）。重啟後遺失的代價是最多多補一次，可接受（ADR-02）。

### 3.5 API（`api/v1/endpoints/data_freshness.py`，新檔，掛於 `main.py`）

兩支皆 `Depends(require_owner)`——報告內含追蹤清單代號，而追蹤清單本身是擁有者資料。

| 方法 | 路徑 | 說明 |
|---|---|---|
| `GET` | `/api/v1/data-freshness?market=tw` | 只讀報告（省略 `market` = 所有啟用市場），不觸發任何抓取 |
| `POST` | `/api/v1/data-freshness/catch-up` | body `{ "markets"?: ["tw","us"], "force"?: false }`；回傳每市場 `{ report, action, reason }` 與 `fetch` 快照 |

回應沿用專案信封 `{ success, data, message? }`。`reason` 為給人看的中文說明（例如「排程 14:30 即將執行，交由排程更新」、「本交易日已補抓過，仍有 2 檔無新資料（可能停牌）」）。

`scheduler.py` 小幅調整：`_scan_after_fetch(market, run_ai_batch: bool = True)`，預設值維持原行為。

## 4. 硬性規則的落實方式

### 4.1 規則 #1：不可整頁 refresh 跳回頂端

- 補抓完成後的刷新一律透過 `refreshKey` prop → 各 panel 既有的 fetch 函式 → `HomeSectionCard` 的「保留舊內容＋遮罩」路徑；**禁止**以 `:key` 重掛 panel、禁止把 `hasData` 歸零。
- `DataFreshnessBar` 各狀態高度差需收斂：以固定最小高度（`min-h`）容納單行狀態，展開「仍落後清單」為使用者主動操作，不會自動撐高頁面把使用者正在看的內容往下推。

### 4.2 規則 #2：同列卡片等高

- 本功能不新增 grid 卡片；`DataFreshnessBar` 為單列元件。若實作時決定改成每市場一張卡的 grid，必須加 `!m-0`（比照 `StockDashboard.vue`）。

| # | 取捨 | 說明與對策 |
|---|---|---|
| **T1** | 報告需讀每檔 JSON 全檔 | `get_coverage_summary()` 經 `load_stock_data()` 讀全檔取最後日期；66 檔約數百毫秒。以 60 秒報告快取＋前端 10 分鐘節流控制。若日後追蹤清單成長到數百檔，再加「只取最後日期」的輕量路徑（仍須放在 `stock_service`，不可另開 DATA_SOURCE 分支） |

| **T3** | 台股補 1 檔與補全部成本相同 | 仍只傳落後標的，換來美股的節省與較少 JSON 寫入；語意也較清楚（log 上看得出補了誰） |
| **T4** | 節流紀錄在記憶體 | 重啟後遺失 → 最多多補一次；不值得為此新增資料表 |
| **T5** | 補抓期間佔住 `fetch_status` | 手動重抓、指數同步按鈕會收到「任務執行中」；排程時窗避讓（§3.4 條件 3）處理最關鍵的排程衝突。若補抓因使用者在時窗前幾分鐘開首頁而拖進排程時間，`_run_if_idle()` 會跳過排程；**下一次開首頁會再補上**（節流鍵為新的 expected_date），可接受 |
| **T6** | 補抓不跑 AI 批次 | 見 ADR-05；AI 報告會晚到下一次排程 |
| **T7** | 只有首頁觸發 | 使用者若書籤直接進個股頁不會觸發；符合需求字面。後續可把 `ensureFresh()` 移到 `AppLayout` |

## 7. 決策紀錄（ADR）

| ID | 決策 | 替代方案與否決理由 |
|---|---|---|
| **ADR-01** | **判斷與派工全在後端**，前端只呼叫一支 `catch-up` | 替代：前端先 `GET` 報告、自己決定再呼叫 `/fetch/trigger`。否決：多分頁競態無法在前端解決、排程時窗與節流邏輯會散在兩端，且 `/fetch/trigger` 未掛 `require_owner` |
| **ADR-02** | 節流鍵 `(market, expected_date)`，**成功補抓過就不再自動重試**；存記憶體 | 替代：固定冷卻時間（例如每 1 小時）。否決：停牌股會每小時打一次 TWSE／yfinance 卻永遠拿不到資料；以 expected_date 為鍵，交易日推進時自然解除 |
| **ADR-03** | 自帶 `asyncio.Lock` 讓「判斷＋登記＋派工」原子化 | 既有 `/fetch/trigger` 的 check-then-act 有競態；自動觸發比人工按鈕更容易同時發生（多分頁、登入事件＋mount） |
| **ADR-04** | 美股休市日用**模組內常數**，不引入 `holidays` / `pandas_market_calendars` | 新增相依套件換來的只是省下「一年多補抓一次」的成本；節流鍵已兜底。常數附來源與年度維護提醒 |
| **ADR-05** | 補抓後**跑策略掃描＋通知，不跑 AI 批次** | 掃描有去重、成本低，且缺了它首頁警示會停在舊日期；AI 批次會實際花費 LLM 費用，自動觸發條件又比排程寬鬆（每次登入都可能），故預設不跑，留到下一次排程 |
| **ADR-06** | 狀態列**不列入** widget 自選 registry、不可關閉 | 自動補抓是系統健康機制而非資訊卡片；允許關閉等於讓使用者在不知情下看舊資料。以「最新時縮成一個小 chip」降低干擾 |

**實作注意事項（給 Sonnet）**

- DATA_SOURCE 分支只能在 `services/stock_service.load_stock_data()`；新程式碼不得自行判斷 json/postgres。
- 不得在爬蟲迴圈加 `time.sleep()` 或繞過 `twse_get_json()`（CLAUDE.md TWSE 限流規則）。
