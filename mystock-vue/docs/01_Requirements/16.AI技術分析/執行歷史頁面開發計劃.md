# LLM 呼叫執行歷史頁面 開發計劃

## 0. 文件說明

**緣起**：使用者參考另一專案（備品／月度計劃審查中台系統，`C:\git_repos\dify-ai-gateway`）的「執行歷史」頁面
（`frontend/src/views/DifyWorkflowHistory.vue` + `DifyWorkflowHistoryController.java`），希望在本專案比照新增一個
「執行歷史」功能：記錄每一次呼叫 AI／LLM 時的**時間、使用了哪個模型、使用了多少 token、花費時間**，並提供查詢畫面。

**本文件範圍**：僅產出**規劃文件**與 **HTML＋JavaScript 靜態雛形畫面**，**不開發任何前後端正式程式碼**（依使用者
指示）。雛形頁面內所有資料皆為寫死的假資料，不呼叫真實 API，純供畫面與互動走查、確認方向後再排入開發排程。

**與既有規格書的關係**：本專案已有 [AI技術分析規劃.md](AI技術分析規劃.md)（AI 技術分析報告 系統開發規格書
v3.4）記載了完整的 AI 診股功能設計。本文件**不修改、不取代**該規格書，而是針對其 **§7 前端設計**尚未涵蓋的一塊
（呼叫層級的執行歷史頁面）提出擴充提案，行文中以「規格書 §X.Y」註記對應章節，供日後併入正式規格書時參照。

## 1. 現況盤點：後端其實已經做完了

比對 Dify 那邊「前後端都要新開發」的情境，本專案在盤點後發現：**這個功能所需的資料表、Repository、API 三層，
在既有的 AI 診股報告模組裡都已經存在**，只是還沒有對應的前端畫面。這是規劃這個功能時最關鍵的一點——真正要做的
開發量遠小於「看起來」的規模。

| 層級 | 現況 | 對應規格書章節 |
|---|---|---|
| 資料表 | `ai_llm_execution`：粒度為「一次 LLM 呼叫一列」，含 provider／model／call_mode／status／token 明細／`estimated_cost_usd`／`elapsed_ms`／時間戳等全部所需欄位 | §5.5 |
| Repository | [ai_execution_repository.py](../../backend/repositories/ai_execution_repository.py) 的 `list_executions()`（分頁＋多條件過濾）、`get_usage_totals()`、`get_usage_by_group()` | — |
| API | `GET /api/v1/ai/executions`、`GET /api/v1/ai/usage`、`GET /api/v1/ai/activity` 三支端點皆已實作於 [ai_analysis.py](../../backend/api/v1/endpoints/ai_analysis.py) | §6.3 |
| 前端 | 只有「歷史**報告**」頁面 `/ai/reports`（[AiReportHistory.vue](../../frontend/src/views/ai/AiReportHistory.vue)），查的是 `ai_analysis_report`（最終產出的診股報告內容），**不是**「每一次呼叫紀錄」。目前**沒有**任何畫面在讀 `/ai/executions` 或 `/ai/usage` | §7.4（僅涵蓋報告頁，未涵蓋執行紀錄頁） |
| 缺口 | `ai_llm_execution` **沒有任何欄位記錄「這次呼叫是被哪個功能觸發的」**（見 §2.1）——現況唯一影響不大（全站只有一個功能會呼叫 LLM），但已確定不會一直是唯一 | — |

**結論**：本功能**幾乎不需要新增後端**。真正要做的開發只有四件事（列入 §6 待辦清單，本次不動工），其中前三件是純前端，第四件是一個欄位量級的小 migration（見 §2.1）：

1. `frontend/src/service/aiAnalysisApi.js` 新增 `listExecutions()` / `getUsage()` 兩個 wrapper function
2. 新增 `frontend/src/views/ai/AiExecutionHistory.vue`
3. `router/index.js` 新增路由、`AppMenu.vue` 新增選單項目
4. `ai_llm_execution` 新增 `view_id` 欄位＋一處呼叫端補傳（§2.1），用於回答「這次呼叫是哪個功能觸發的」

「歷史報告」（What，AI 判斷出的結論）與「執行歷史」（How，這次判斷花了多少錢多少時間、成功了沒）是兩張不同的表、
回答兩個不同的問題，兩個頁面應並存、互不取代——這點也是為什麼 Dify 專案要獨立做一個「執行歷史」頁面，而不是塞進
既有的報告列表裡。

## 2. 參考頁面 vs. 本專案欄位對照

Dify 的「執行歷史」是通用 Workflow 執行紀錄（可套用在備品審查、月度計劃審查等任何 Workflow），本專案的
`ai_llm_execution` 是專為「AI 診股」單一用途設計，欄位語意更貼近「呼叫一次 LLM」本身而非「跑一個工作流程」。對照
如下（「本專案沿用」＝畫面設計直接比照；「本專案改造」＝概念相通但欄位意義不同，需要調整呈現方式；
「本專案新增」＝Dify 沒有但既有資料多提供的欄位，建議一併呈現）。

| Dify 畫面欄位／篩選 | 對應概念 | `ai_llm_execution` 欄位 | 處理方式 |
|---|---|---|---|
| 執行模式（BLOCKING／STREAMING／JOB） | 呼叫方式 | `call_mode`（`blocking`／`streaming`） | 沿用（本專案目前只有 `blocking`，`streaming` 保留擴充） |
| Workflow 名稱 | 呼叫的「對象」 | 無對應欄位——本專案是單一「AI 診股」用途，沒有多 Workflow 概念 | 改造：以 **Provider／模型**（`provider` + `model`）取代，這才是本專案「叫用了哪個服務」的真正變因 |
| 提交者 | 誰觸發的 | `submitted_by`（固定 `owner`，單人自用系統） | 沿用但降權：單人系統下此欄位資訊量低，可移入明細而非列表 |
| 狀態（COMPLETED／FAILED／PENDING／RUNNING） | 執行狀態 | `status`（`pending`／`succeeded`／`failed`） | 沿用，標籤語意對應 COMPLETED→succeeded、FAILED→failed、PENDING/RUNNING→pending |
| 耗時 | 花費時間 | `elapsed_ms`（毫秒） | 沿用，換算為秒顯示（`(elapsed_ms/1000).toFixed(2)+'s'`） |
| Tokens | 用量 | `input_tokens` / `output_tokens` / `total_tokens`（含快取 `cache_read_tokens`/`cache_write_tokens`） | 新增：Dify 只顯示合計，本專案可額外顯示輸入／輸出拆分＋**預估成本 `estimated_cost_usd`**（Dify 頁面沒有這欄，但本專案定價表已現成，見規格書 §10.4） |
| UUID | 追蹤代碼 | `execution_uuid` | 沿用 |
| 建立時間 | 觸發時間 | `created_at` | 沿用 |
| （無） | 標的快照 | `symbol` / `market_type` / `trade_date` | 新增：本專案特有維度，「這次呼叫是在分析哪一檔股票」，比 Dify 的提交者更有查詢價值，建議取代提交者成為主要篩選/顯示欄位 |
| （無） | 是否為試跑 | `is_dry_run` | 新增：對應規格書 §4.6 的強制重產（`force:true`），預設排除於統計外，畫面上以篩選開關呈現 |
| 明細「傳入 Inputs／回傳 Outputs JSON」 | 請求／回應內容 | `request_meta` / `response_meta`（**僅中繼資料，不含 prompt 全文與圖片**，見規格書 §8.2） | 改造：Dify 存的是完整 Workflow 輸入輸出，本專案基於機敏資訊規範刻意不存 prompt 全文，明細改顯示 `max_tokens`／`stop_reason`／`provider_request_id`／圖片位元組數等中繼欄位 |
| （無） | 彙總儀表 | `GET /ai/usage` 的 `totals`（呼叫數／成功／失敗／快取命中／總 token／總成本） | 新增：Dify 頁面沒有這塊，但既有 API 已支援，建議在列表上方加一排 KPI 卡片（詳見 §3.3），比單純的「共 N 筆」更有資訊量 |

### 2.1 補一個欄位：這次呼叫是「哪個功能」觸發的（`view_id`）

Dify 的「Workflow 名稱」在本專案原本被 §2 表格改造成「Provider／模型」，理由是「本專案只有一個 AI 診股用途，沒有
多 Workflow 概念」。**這個前提現在需要修正**：[Phase5-三層式 AI 決策引擎與戰情室.md](Phase5-三層式%20AI%20決策引擎與戰情室.md)
第 71 行明確寫著「AI 分析 RESTful API…已完成（含用量／執行紀錄查詢）」，也就是說 Phase 5 規劃的**戰情室批次掃描**
會沿用同一套 `ai_analysis.py` API 與 `ai_llm_execution` 執行紀錄表，而不是另開一套。屆時同一張表會混著兩種完全不
同性質的呼叫來源：

| 觸發來源 | 現況 | 呼叫方式 |
|---|---|---|
| 個股頁「AI 診股報告」按鈕 | 現行唯一來源 | 使用者手動點擊，一次一檔 |
| 戰情室批次掃描 | Phase 5 規劃中，**尚未開發** | 排程／批次，橫掃整份監控清單 |

執行歷史頁面若不能分辨「這次呼叫是哪個功能造成的」，等 Phase 5 上線後就無法回答「這個月的 AI 成本，多少是使用者
自己點出來的、多少是戰情室自動掃出來的」——這正是使用者在雛形畫面走查後提出「加上在哪個功能所執行的」的動機。

**做法（比照既有慣例，不是新發明一套）**：`activity_log.view_id VARCHAR(60)`（規格書 §5.6，「觸發來源畫面」）這個
欄位設計已經證明好用，直接原樣加到 `ai_llm_execution`：

```sql
-- V15__Add_view_id_to_ai_llm_execution.sql（草案，本次不執行，供未來實作參照）
ALTER TABLE ai_llm_execution ADD COLUMN view_id VARCHAR(60);
CREATE INDEX IF NOT EXISTS idx_ai_exec_view_id ON ai_llm_execution (view_id, created_at DESC);
```

寫入時機：`ai/recorder.py` 的 `start_execution()` 呼叫時一併帶入（呼叫端 `ai_analysis.py` 其實早就知道自己是哪個
view——同一支函式呼叫 `recorder.log_cached(view_id="stock_dashboard", ...)` 時已經在傳這個字串了，只是目前沒有
一併傳給 `start_execution()`／寫進這張表）。**不做成外鍵、不另建對照表**，沿用 `activity_log` 已有的自由字串慣例
即可，日後 Phase 5 戰情室的呼叫端只要傳自己的 `view_id`（例如 `war_room_batch`，實際命名以 Phase 5 定案為準）就
自動能在本頁被分辨出來，不需要再改一次 schema。

**為何不用 join `activity_log` 代替新欄位**：`activity_log` 的 `AI_REPORT_GENERATE` 事件以 `rel_id=report_id`
關聯回報告，但同一個 `report_id` 可能有多次 `attempt_no`（重試），僅憑 `report_id` join 不保證對應到「這一次」
執行紀錄，容易在重試情境下對錯列。直接在 `ai_llm_execution` 補一個屬於自己的欄位才是唯一可靠做法。

**舊資料**：欄位新增前已存在的執行紀錄，`view_id` 會是 `NULL`，畫面上顯示為「（早期資料・未記錄）」，不可回填猜測。

### 3.3 用量彙總卡片

資料來源 `GET /ai/usage?group_by=model&date_from=&date_to=`（規格書 §6.3）的 `totals` 區塊，直接映射為 6 張等高
KPI 卡片：

| 卡片 | 欄位 | 說明 |
|---|---|---|
| 總呼叫次數 | `call_count` | 含失敗，這是「花錢的次數」而非「使用者點擊次數」（規格書 §10.3：兩者不相等） |
| 成功 | `success_count` | 綠色系 |
| 失敗 | `failed_count` | 紅色系，持續偏高代表有系統性問題在燒錢（規格書 §10.3 提醒） |
| 快取命中（省下的呼叫） | `cached_hit_count` | 來自 `activity_log` 的 `AI_REPORT_CACHED`，代表「當日已有報告、沒有真的呼叫 LLM」的次數——這是本模組成本設計是否奏效的直接證據 |
| 總 Token 用量 | `total_tokens` | 輸入＋輸出 |
| 預估總成本 | `estimated_cost_usd` | 以 USD 顯示，小數 4 位 |

> **CLAUDE.md 鐵則 2**（卡片等高）：這 6 張卡片是同列 Grid，雛形與未來實作皆需在卡片項目加 `!m-0` 中和
> `_utils.scss` 的 `.card:last-child` 舊規則，避免最後一張卡比同列矮一截。雛形畫面已用等高 Grid + 統一 padding
> 呈現，供實作時比對。

### 3.5 執行紀錄資料表

沿用 Dify 頁面「單列一次呼叫、可展開明細」的資訊架構，欄位改為：

| 欄位 | 資料來源 | 呈現方式 |
|---|---|---|
| 操作 | — | 「明細」按鈕（`pi-info-circle`），開啟 §3.6 Dialog |
| 建立時間 | `created_at` | `YYYY-MM-DD HH:mm:ss` |
| 標的 | `symbol` + `market_type` | 例：`2330（台股）`，`market_type` 以既有 `useMarket()` 顯示慣例呈現 |
| 功能 | `view_id`（新增欄位，見 §2.1） | Tag＋文字，例：`個股 AI 診股報告`；`NULL` 顯示「（早期資料）」 |

| 呼叫模式 | `call_mode` | Tag：`blocking`／`streaming` |

| 預估成本 | `estimated_cost_usd` | `$0.0192`，`null` 顯示「未知」（規格書 §10.4：找不到單價不可用猜的） |

預設 20 筆／頁，可選 10／20／50。

### 3.6 明細 Dialog

點「操作」開啟，呈現 `ai_llm_execution` 單列全貌，資訊分區比照 Dify 明細 Dialog 的卡片式排版：

- **基本資訊區**（等高小卡片 Grid）：UUID、觸發功能（`view_id`，見 §2.1）、Provider／模型、呼叫模式、狀態、標的
  （symbol/market/trade_date）、嘗試次數 `attempt_no`、`prompt_version`、是否試跑 `is_dry_run`
- **用量與成本區**：`input_tokens` / `output_tokens` / `cache_read_tokens` / `cache_write_tokens` / `total_tokens`
  （生成欄位）／ `image_bytes` / `estimated_cost_usd`
- **時間軸區**：`started_at` → `completed_at`，並標示 `elapsed_ms`
- **錯誤資訊**（僅 `status='failed'` 時顯示）：`error_code` / `error_message`，紅底 Message 區塊
- **中繼資料 JSON 預覽**：`request_meta` / `response_meta` 兩顆按鈕開 JSON Preview（比照 Dify 的
  「傳入 Inputs／回傳 Outputs JSON」按鈕與 `TcciJsonPreviewDialog.vue` 用法），**明確排除** prompt 全文與圖片
  base64（規格書 §8.2 機敏資訊規範——這兩張表本來就沒存這些內容，不是畫面刻意隱藏）
- **關聯**：若 `report_id` 存在，提供「查看對應診股報告」連結，帶往 `/ai/reports/{report_id}`（串接既有頁面，
  不重複實作報告呈現邏輯）

### 3.7 互動與狀態、既有鐵則遵循

| 情境 | 規則 |
|---|---|
| 篩選重新查詢 | **不得整頁 loading 卸載表格**（CLAUDE.md 鐵則 1）。沿用 `AiReportHistory.vue` 的作法：`loading` 只驅動 DataTable 內建的 `:loading` 遮罩，表格本體與捲動位置不受影響 |
| 無查詢結果 | 沿用 Dify 頁面的空狀態設計（`pi-inbox`＋提示文字） |
| 查詢失敗 | Toast 顯示錯誤（比照既有 `catch` 慣例），不清空目前已顯示的資料 |
