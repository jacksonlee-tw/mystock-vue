## 1. 核心設計原則

### 1.1 為什麼要獨立模組？

| 設計決策 | 理由 |
| :--- | :--- |
| **關注點分離** | 常規順勢策略（均線突破）與極端逆勢策略（接刀）的觸發邏輯、風險承受度、資金管理完全不同，混在一起會互相干擾 |
| **Hardcode 防線** | 常規策略允許使用者自由調參（YAML），但本模組的安全護欄**必須在程式碼層級強制實作**，禁止透過外部設定繞過 |
| **資金隔離** | 抄底策略的資金池須與主投資組合隔離，確保即使全數虧損也不影響整體資產 |
| **休眠式啟動** | 常規策略每日掃描，本模組平時休眠，僅在大盤環境觸發門檻時才被喚醒 |

### 1.2 策略理論基礎

「跌停板買進」是極端逆勢交易，風險與機會並存：

| 面向 | 說明 |
| :--- | :--- |
| **致命風險 — 流動性枯竭** | 買入後跌停鎖死，隔日跳空開低甚至連續跌停，無法執行停損 |
| **致命風險 — 基本面崩壞** | 個股單獨跌停常伴隨財報造假、掉單等利空，跌停是價值重估而非錯殺 |
| **獲利契機 — 恐慌超賣** | 系統性風險引發的無差別拋售，會讓好公司被錯殺至遠低於真實價值 |
| **獲利契機 — 極端盈虧比** | 若在真正底部買入，後續反彈幅度通常極大 |

> **核心前提**：本策略僅在「系統性恐慌導致的錯殺」場景下有效，不適用於個股基本面崩壞的場景。系統設計必須以嚴格濾網排除後者。

## 2. 觸發條件與高勝率情境

### 2.1 策略總覽

本模組包含 **一個核心策略**，以唯一 `strategy_id` 識別。該策略的觸發需要「大盤環境前提」+「個股條件」**同時滿足**。

#### `crisis_rebound` — 權值股恐慌錯殺反彈

| 屬性 | 說明 |
| :--- | :--- |
| **模組歸屬** | `extreme_risk`（專屬風險模組） |
| **風險等級** | `CRITICAL` |
| **適用市場** | 僅台股（`tw`）— 美股無漲跌停機制，需另行設計 |
| **預設狀態** | 休眠（`dormant`），大盤條件觸發後才進入掃描 |

### 2.2 大盤環境前提（Global Market Lock）

模組平時處於**休眠狀態**。以下任一條件成立時，模組被喚醒並開始掃描個股：

| 喚醒條件 ID | 條件 | 說明 |
| :--- | :--- | :--- |
| `market_crash` | 大盤加權指數單日跌幅 ≥ **3%** | 系統性恐慌拋售，好壞公司一起跌停 |
| `market_extreme_bias` | 大盤指數距離 20MA 負乖離 ≥ **8%** | 整體市場超賣，接近歷史極端 |
| `vix_spike` | VIX 恐慌指數穿越特定閾值（未來擴充） | 需額外接入 VIX 資料源 |

> **勝率最高場景**：大盤單日暴跌 > −4%，觸發法人停損機制與融資斷頭的多殺多，大型權值股被無差別拋售。此類錯殺股在大盤止穩後反彈最快。

### 2.3 個股觸發條件（三種情境）

大盤環境前提成立後，對白名單內的個股逐一掃描以下條件：

#### 情境 A：跌停打開 + 爆量（勝率最高）

| 條件 | 門檻 | 說明 |
| :--- | :--- | :--- |
| 盤中曾觸及跌停價 | `low ≤ limit_down_price` | 股票曾跌停 |
| 收盤價 > 跌停價 | `close > limit_down_price` | 跌停板被買盤敲開 |
| 成交量爆量 | `volume ≥ MA_Volume_20 × 2.0` | 有大資金底部承接 |
| 收盤留下影線 | `close > (high + low) / 2` | 非長上影線的誘多假突破 |

#### 情境 B：連續大跌 + 極端負乖離

| 條件 | 門檻 | 說明 |
| :--- | :--- | :--- |
| 20MA 負乖離 | `BIAS_20 ≤ −25%` | 月線超賣到歷史極端 |
| 60MA 負乖離 | `BIAS_60 ≤ −30%` | 季線也顯示極端超賣 |
| 成交量確認 | `volume ≥ MA_Volume_5 × 1.5` | 有換手跡象 |

#### 情境 C：融資斷頭清洗（僅台股）

| 條件 | 門檻 | 說明 |
| :--- | :--- | :--- |
| 融資連續減少 | 融資餘額連續 3 天減少且減幅 ≥ 5% | 散戶被斷頭強制出場 |
| 三大法人翻買 | 外資或投信同日轉為淨買超 | 法人在散戶出逃時趁低承接 |
| 股價條件 | 收盤價距離 60MA 負乖離 ≥ −15% | 技術面已超賣 |

### 2.4 觸發判定虛擬碼

```python
def scan_crisis_rebound(market_data, stock_data, config):
    """極端抄底策略掃描主邏輯"""

    # ── 第一關：大盤環境前提 ──────────────────────
    index_change = market_data.index_daily_change_percent
    index_bias_20 = market_data.index_bias_20ma

    market_awakened = (
        index_change <= config.market_crash_threshold      # 預設: -3.0
        or index_bias_20 <= config.market_bias_threshold   # 預設: -8.0
    )
    if not market_awakened:
        return []  # 大盤正常，模組維持休眠

    # ── 第二關：白名單過濾 ──────────────────────
    alerts = []
    for stock in stock_data:
        if stock.id not in config.universe_whitelist:
            continue  # 非大型權值股，跳過

        # ── 第三關：流動性確認 ──────────────────
        if stock.volume < stock.ma_volume_20 * config.volume_multiple:
            continue  # 無量，跳過

        # ── 第四關：個股極端條件 ────────────────
        triggered = False
        scenario = None

        # 情境 A：跌停打開 + 爆量
        if (stock.low <= stock.limit_down_price
            and stock.close > stock.limit_down_price
            and stock.close > (stock.high + stock.low) / 2):
            triggered = True
            scenario = "limit_down_opened"

        # 情境 B：極端負乖離
        elif (stock.bias_20 <= config.oversold_bias_20
              and stock.bias_60 <= config.oversold_bias_60):
            triggered = True
            scenario = "extreme_negative_bias"

        # 情境 C：融資斷頭（僅台股）
        elif (stock.market == "tw"
              and stock.margin_decrease_3d >= config.margin_decrease_pct
              and stock.institutional_net_buy > 0):
            triggered = True
            scenario = "margin_call_washout"

        if triggered:
            alerts.append(CrisisAlert(
                stock=stock,
                scenario=scenario,
                signal_strength=classify_strength(stock, scenario)
            ))

    return alerts
```

## 3. 三道防線設計（Hard Guardrails）

> [!CAUTION]
> 以下三道防線**必須在 Python 程式碼層級 Hardcode 實作**，不允許透過 YAML 設定檔或 API 參數覆蓋。這是保護真金白銀的最後護城河。

### 3.1 第一道：白名單過濾（Universe Filter）

| 規則 | 實作方式 |
| :--- | :--- |
| 此模組**拒絕**對中小型股計算任何策略 | 程式碼層級 `assert` |
| 僅允許 `config/universe.yaml` 中標記為 `is_large_cap: true` 或 `benchmark_constituent: true` 的標的 | 白名單載入後不可在 Runtime 動態擴充 |
| 初期建議白名單 | 台積電（2330）、0050、0056、鴻海（2317）等大型權值股/ETF |

**設計理由**：杜絕抄底到因財報造假而暴跌、甚至下市的小型妖股，確保標的具備「大到不能倒」的流動性。

### 3.2 第二道：流動性確認（Liquidity Check）

| 規則 | 門檻 |
| :--- | :--- |
| 當日成交量 ≥ 過去 20 日均量 × 2 倍 | Hardcode 下限 |
| 若為跌停打開情境，收盤價**必須**大於跌停價 | 拒絕「無量跌停鎖死」標的 |

**設計理由**：確保有足夠的市場對手盤提供流動性，避免買入後無法脫手。

### 3.3 第三道：雙重絕對停損（Double Stop-Loss）

| 停損類型 | 規則 | Hardcode 參數 |
| :--- | :--- | :--- |
| **價格停損** | T+1 或 T+2 日收盤價 < T 日最低價 → 無條件觸發停損 | 不可調 |
| **時間停損** | 買入後 3 個交易日內未出現 ≥ 3% 反彈 → 強制平倉 | 天數與百分比不可調 |

**設計理由**：抄底策略的核心是「吃恐慌錯殺的短線反彈」。如果買入後沒有立刻反彈，代表市場判定不是錯殺而是真有問題，必須立刻撤退。

## 8. 警示通知機制

### 8.1 通知訊息範本

極端抄底警示使用**紅色高危格式**，與常規均線警示（藍色）明顯區隔：

```
🔴🔴🔴 【極端風險 — 跌停打開反彈】
━━━━━━━━━━━━━━━━━━
⚠️ 模組：Crisis Alpha（極端抄底）
📌 標的：2330 台積電
━━━━━━━━━━━━━━━━━━
🌊 大盤：加權指數 -4.2%（觸發市場恐慌門檻）
📉 跌停價：$832 → 收盤 $850（跌停已打開）
📊 乖離率：月線 -12.3% / 季線 -18.7%
📦 成交量：125,000 張（20日均量 3.2×）
🏦 籌碼：外資今日買超 15,000 張
━━━━━━━━━━━━━━━━━━
💀 停損規則（不可違反）：
   · 價格停損：$832（T日最低價）
   · 時間停損：3 日內無 +3% 反彈 → 平倉
💰 限額：零股 / 單筆 ≤ NT$30,000
━━━━━━━━━━━━━━━━━━
🤖 執行模式：僅通知（手動評估）
```

### 8.2 訊號強度分級

| 等級 | 定義 | 觸發後行為 |
| :--- | :--- | :--- |
| `strong` | 大盤暴跌 ≥ 4% + 跌停打開爆量 + 法人買超 | Phase 5: 強烈通知；Phase 6: 自動小額派單 |
| `moderate` | 大盤跌 ≥ 3% + 極端負乖離但未跌停 | 通知觀察，不自動下單 |
| `weak` | 僅大盤環境條件成立，個股條件只滿足一項 | 記錄但不通知 |

## 9. Phase 6：自動派單執行引擎

> [!CAUTION]
> Phase 6 涉及真金白銀。正式上線前必須完成「安全上線三部曲」，不可跳過任何階段。

### 9.1 執行流程

```
CrisisAlert 產生
      │
      ▼
┌──────────────────────────┐
│ 1. Kill Switch 檢查       │──── 已啟動 → 阻斷，僅記錄
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 2. 資金與權重覆核         │
│  · 查詢券商帳戶可用餘額    │──── 餘額不足 / 超過 5% 上限 → 阻斷
│  · 檢查當日已下單數量      │
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 3. 保險絲檢查             │
│  · 單筆 ≤ NT$30,000      │──── 違反任一 → 阻斷
│  · 同標的當日 ≤ 1 次      │
│  · 僅限零股委託           │
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 4. 委託單生成             │
│  · 限價單（觸發價 +2~3檔） │
│  · 記錄完整 Audit Log     │
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 5. 發送至券商 API         │
│  · 訂閱成交回報            │
│  · 推播實際成交/未成交狀態  │
└──────────────────────────┘
```

### 9.2 保險絲機制（Circuit Breakers）

| 保險絲 | 規則 | 層級 |
| :--- | :--- | :--- |
| **單筆金額鎖** | `max_single_order ≤ NT$30,000`，初期強制零股委託 | Hardcode |
| **防連發鎖** | 同一股票同一交易日最多 1 次買進委託 | Hardcode |
| **日限額鎖** | 全模組當日總委託金額 ≤ NT$100,000 | Hardcode |
| **全局 Kill Switch** | 前端一鍵啟動 → 切斷所有 API 下單權限，轉純通知模式 | API + UI |

### 9.3 安全上線三部曲（Phased Rollout）

| 階段 | 名稱 | 內容 | 退出條件 |
| :--- | :--- | :--- | :--- |
| **階段一** | 訊號乾跑（Dry Run） | 系統按真實邏輯產生虛擬訂單並記錄，不實際下單 | 連續 30 天觸發時機正確率 ≥ 90% |
| **階段二** | 模擬交易（Paper Trading） | 串接券商模擬 API，測試委託發送、撤銷、成交回報 | 所有保險絲正常運作，無異常觸發 |
| **階段三** | 真倉上線（Live Trading） | 切換至正式 API 憑證，啟動零股小額派單 | 人工確認前兩階段結果無誤 |

## 12. 驗收標準

### 功能驗收（Phase 5）

| 編號 | 驗收項目 | 通過條件 |
| :--- | :--- | :--- |
| AC-1 | 大盤環境鎖正常運作 | 大盤跌幅 < 3% 時模組保持休眠，不產生任何掃描或警示 |
| AC-2 | 白名單嚴格過濾 | 非白名單標的在任何條件下均不觸發警示，以 unit test 驗證 |
| AC-3 | 跌停打開情境觸發 | 以歷史資料（如 2020/03 股災期間 2330 資料）驗證情境 A 正確觸發 |
| AC-4 | 極端負乖離情境觸發 | 月線負乖離 ≤ −25% 且季線 ≤ −30% 時正確觸發 |
| AC-5 | 流動性過濾有效 | 無量跌停鎖死的標的被正確排除 |
| AC-6 | 通知格式正確 | Telegram 訊息包含大盤背景、觸發詳情、停損規則 |
| AC-7 | API 回應符合契約 | `/alerts?module=extreme_risk` 與 `/extreme-risk/status` 回應格式正確 |

### 功能驗收（Phase 6）

| 編號 | 驗收項目 | 通過條件 |
| :--- | :--- | :--- |
| AC-8 | Dry Run 訂單記錄 | 虛擬訂單完整記錄觸發時間、標的、價格、理由 |
| AC-9 | 保險絲全數生效 | 單筆 > NT$30,000 / 同股同日第 2 次 / 總額 > NT$100,000 → 阻斷 |
| AC-10 | Kill Switch 立即生效 | 啟動後 0.5 秒內切斷所有下單權限 |
| AC-11 | 限價單正確生成 | 委託價 = 觸發價 + 2~3 檔，非市價單 |

### 非功能驗收

| 編號 | 驗收項目 | 通過條件 |
| :--- | :--- | :--- |
| NF-1 | Guardrails 不可繞過 | 三道防線參數無法透過 YAML / API / 環境變數覆蓋，以 code review + test 驗證 |
| NF-2 | 模組隔離性 | 極端抄底模組的任何異常（crash / timeout）不影響常規均線策略的正常運作 |
| NF-3 | 審計日誌完整 | 每筆 alert + 每筆 order（含阻斷原因）均有完整 log 記錄，可事後追溯 |
