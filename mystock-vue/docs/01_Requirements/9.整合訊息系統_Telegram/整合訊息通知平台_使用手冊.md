## 1. 系統概觀與名詞對照

整合訊息通知平台負責把 MyStock 系統內部發生的事件（策略警示、資料抓取結果、系統異常等）送到您指定的 Email 或 Telegram。整體資料流是：

```
事件發生（策略掃描 / 每日抓取 / 系統健康檢查）
        ↓
訂閱規則（誰要收到這類事件？符合什麼條件？）
        ↓
收件人與端點（這個人／群組的 Email 或 Telegram 是什麼？當下能不能發？）
        ↓
訊息模板（渲染成實際文字內容）
        ↓
管道（Email／Telegram）實際送出
        ↓
發送紀錄（成功/失敗，可查可重送）
```

**名詞對照表**

| 名詞 | 意思 |
|---|---|
| 管道（Channel） | 發送訊息的技術管道，目前有 Email、Telegram 兩種 |
| 收件人（Recipient） | 一個實際的人，例如「我自己」「家人 B」 |
| 端點（Endpoint） | 收件人底下具體的一個收件位址，例如某個 Email 信箱、某個 Telegram 對話。一個收件人可以有多個端點（Email + Telegram 都設） |
| 共用端點（Shared Endpoint） | 不屬於任何特定收件人的端點，用於 Telegram 群組（多人共用） |
| 訂閱規則（Subscription） | 「什麼事件、什麼條件 → 送給誰」的規則 |
| 事件（Event） | 系統內部發生的一件事，例如一筆策略警示訊號 |
| 訊息（Message） | 事件經過規則比對、政策閘門後，實際排入發送佇列的一則訊息 |
| 系統擁有者（Owner） | 能登入管理介面的人，用密碼登入，非收件人身分 |

## 2. 首次啟用前的準備（.env 設定）

在打開管理介面之前，`backend/.env` 需要先設定好以下項目（複製自 `backend/.env.example`，僅列出必要項目）：

| 變數 | 說明 |
|---|---|
| `NOTIFY_ENABLED` | 設為 `true` 才會啟動整個通知平台（含 Telegram 長輪詢監聽） |
| `NOTIFY_SECRET_KEY` | Fernet 加密金鑰，用來加密 SMTP 密碼、Telegram Bot Token 等機敏設定；可用 `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` 產生 |
| `OWNER_PASSWORD_HASH` | 管理介面登入密碼的 bcrypt 雜湊值（**不是明文密碼**）；可用 `python -c "import bcrypt; print(bcrypt.hashpw(b'你的密碼', bcrypt.gensalt()).decode())"` 產生後貼上 |
| `DATA_SOURCE` | 需為 `postgres`（通知平台的收件人、訂閱規則等資料都存在 PostgreSQL，與股票資料的 JSON/Postgres 雙軌無關） |

改完 `.env` 後，需要有一份已套用 `db/migration/V3__Create_notification_platform.sql`（含之後的 `V4`、`V5` 等）的 PostgreSQL 資料庫（本機開發用 `docker compose up -d` 即會自動跑 flyway migration）。

以上都設定好、後端啟動成功後，才會出現本手冊後續介面。

## 3. 登入管理介面

1. 瀏覽器開啟 `/notify/channels`（例如 `http://localhost:5173/notify/channels`）
2. 若尚未登入，會自動導向登入頁「通知設定管理」
3. 輸入 `.env` 裡 `OWNER_PASSWORD_HASH` 對應的明文密碼 → 點 **登入**
4. 登入後，左側選單「通知設定」下會出現五個子選單：**管道設定、收件人、訂閱規則、訊息模板、發送紀錄**

> 登入狀態透過瀏覽器 Cookie 保存，關閉分頁後下次仍需重新登入視 Cookie 效期而定。

## 4. 管道設定：Email

路徑：左側選單 → **通知設定 → 管道設定** → 左邊 **Email** 卡片

| 欄位 | 說明 |
|---|---|
| SMTP 主機 | 例如 `smtp.gmail.com` |
| SMTP 埠 | 例如 `587`（TLS）或 `465`（SSL） |
| 帳號 | SMTP 登入帳號，通常等於寄件信箱 |
| 密碼 | SMTP 密碼或應用程式密碼（Gmail 需使用「應用程式密碼」，不是登入密碼） |
| 寄件人名稱 | 收件人信箱看到的寄件人顯示名稱 |
| 寄件信箱 | 實際寄件地址 |

**設定步驟**
1. 依上表填入 6 個欄位 → 點 **儲存設定**
2. 點 **連線測試**，系統會嘗試與 SMTP 主機建立連線並驗證登入，成功會顯示連線成功訊息
3. 測試通過後，把 Email 卡片右上角開關切成 **開啟**，狀態應從「設定不全」變成「正常」

> 密碼欄位儲存後畫面只會顯示「未變更則留空」，這是機敏欄位遮蔽（不會把密碼明文顯示回來）。若要更換密碼，直接輸入新密碼儲存即可；留空儲存代表沿用原本設定，不會被清空。

## 5. 管道設定：Telegram

路徑：左側選單 → **通知設定 → 管道設定** → 右邊 **Telegram** 卡片

### 5.1 建立 Telegram 機器人，取得 Bot Token
1. 在 Telegram 搜尋 **@BotFather** 並開啟對話
2. 傳送 `/newbot`，依提示輸入機器人名稱與帳號（帳號需以 `bot` 結尾）
3. 建立完成後，BotFather 會回傳一組 Token（格式類似 `123456789:AAG...`），複製起來

### 5.2 在系統填入 Token
1. 「機器人憑證」欄位貼上剛複製的 Token
2. 點 **儲存設定**

### 5.3 連線測試
1. 點 **連線測試**，系統會呼叫 Telegram 的 `getMe` API 驗證 Token
2. 成功會顯示「已連接機器人：@您的機器人帳號」，並常態顯示在卡片上（不用重新測試也看得到，重新整理頁面也會保留）
3. 失敗會顯示錯誤原因（例如 Token 打錯、Token 已被撤銷）

### 5.4 啟用管道
確認測試通過後，把 Telegram 卡片右上角開關切成 **開啟**，狀態應從「設定不全」變成「正常」。

> 只完成 5.1–5.4 代表「機器人本身」設定好了，**還沒有任何人會收到訊息**。要讓特定的人或群組實際收到通知，請接續第 6 章「綁定」。

## 6. 收件人與端點管理

路徑：左側選單 → **通知設定 → 收件人**

### 6.1 新增收件人
1. 點右上角 **新增收件人**
2. 填寫顯示名稱（例如「我自己」「家人 B」）
3. 可選擇加入既有收件群組（沒有的話留空，群組建立方式見第 7 章）
4. 點 **建立**

### 6.2 幫收件人加 Email 端點
1. 該收件人卡片右上角點 **加 Email**
2. 輸入收件信箱 → 點 **建立並寄出驗證信**
3. 系統會寄出一封驗證信到該信箱；收件人需完成信件內的驗證動作，端點狀態才會從「待驗證」變成「已驗證」
4. 尚未驗證前，該端點不會收到任何正式通知（僅供之後的「測試發送」使用）
5. 若信件遲遺失，可在該端點列點 **重寄驗證信**

### 6.3 幫收件人綁定 Telegram 端點
1. 該收件人卡片右上角點 **綁 Telegram**
2. 系統彈出一組 **4 位數綁定碼**（15 分鐘內有效）
3. 請該收件人本人在 Telegram 搜尋您的機器人 → 點擊「開始 / Start」→ 直接把這組 4 位數字當作訊息傳給機器人
4. 機器人會自動回覆「綁定成功」，端點立即視為已驗證，開始接收通知
5. 收件人日後可在 Telegram 對話中傳送 `/unbind` 自行解除綁定

### 6.4 測試發送與停用端點
- 每個端點列都有 **測試發送**（紙飛機圖示）按鈕，可立即發一則測試訊息，不會計入正式發送紀錄
- 點 **✕** 可停用端點（保留歷史紀錄，不是刪除；停用後該端點不再收到通知）

### 6.5 專屬自助連結
每位收件人卡片下方有「自助設定連結」，點 **撤銷重產** 會產生一組新的一次性連結網址（**明文只顯示這一次，請立刻複製**），把連結傳給該收件人本人，讓他不需帳號密碼即可自行調整自己的通知偏好（見第 11 章）。重新產生會讓舊連結立即失效。

## 7. 收件群組與共用端點（Telegram 群組）

### 7.1 收件群組（多位「收件人」的集合）
路徑：收件人頁面右上角 → **收件群組**
1. 輸入群組名稱 → 點 **＋** 建立
2. 之後在「新增收件人」或編輯收件人時，把該收件人加入此群組
3. 訂閱規則的目標對象可以直接選整個群組，群組內所有收件人的所有端點都會收到

### 7.2 共用端點（Telegram 群組聊天室，不屬於任何個人）
若您想讓通知直接發到一個 Telegram **群組聊天室**（而非某個人的私訊），流程不同於 6.3：
1. 收件人頁面點 **產生群組綁定碼**（畫面上對應「群組（共用端點）綁定碼」功能）
2. 把機器人加入該 Telegram 群組
3. 在群組中傳送這組綁定碼給機器人
4. 系統會自動建立一個「共用端點」，列在收件人清單下方「共用端點」區塊

> **重要**：共用端點預設的發送模式是「僅緊急」（`critical_only`），而策略警示訊號一律是一般（`info`）等級，**預設不會即時發到群組**，會被併入每日摘要才送出。若希望群組能即時收到策略警示，請見第 12 章 FAQ 的調整方式。

## 8. 訂閱規則：決定誰收到什麼

路徑：左側選單 → **通知設定 → 訂閱規則**

管道設定好、收件人也綁定了，**還需要至少一條訂閱規則**，否則不會有任何事件送到任何人。

### 8.1 新增規則
1. 點右上角 **新增規則**
2. **規則名稱**：自訂，例如「策略警示 → 我自己」
3. **① 事件類型**：從下拉選單選一種（見 §13.1 事件類型一覽），策略警示要選 **策略警示訊號（ALERT_SIGNAL）**
4. **② 過濾條件**（可留空 = 不過濾，收該事件類型的全部訊號）：
   - 市場：`tw`（台股）／`us`（美股）
   - 訊號強度：`strong`／`moderate`／`weak`
   - 訊號類型：`BUY`／`SELL`／`WARNING`
   - 策略分類：`technical`（技術面）／`chip`（籌碼面）／`fundamental`（基本面）
   - 同一項目內多選是「或」；不同項目之間是「且」
5. **③ 目標對象**：三選一——收件群組、單一收件人、或（進階）單一端點
6. 點 **建立規則**

### 8.2 規則測試（不會真的發送）
點右上角 **規則測試**，選一筆內建的模擬訊號，畫面會列出哪些已啟用規則會命中、命中後會送到誰，方便下規則後立即確認邏輯是否符合預期。

### 8.3 啟用／停用規則
每條規則卡片右上角有開關，可隨時停用而不刪除規則。

## 9. 訊息模板：客製化文案

路徑：左側選單 → **通知設定 → 訊息模板**

- 左側選事件類型，右側切換 Email／Telegram 分頁
- 未自訂時會標示「使用預設模板」，系統會用內建的通用文案，**不會因為沒設定模板而漏發訊息**
- 內文可用左下角「可用變數」清單插入變數（點一下變數名稱即插入游標處），例如 `{{ stock_id }}`、`{{ stock_name }}`、`{{ strategy_name }}`
- 改完點 **預覽** 可用範例資料看實際渲染結果，確認無誤後點 **儲存模板**
- Email 另有「主旨」欄位可自訂；Telegram 沒有主旨，第一行文字通常作為標題用途

> 修改模板只影響文案顯示，不影響任何路由或發送邏輯，改壞了也不會讓系統壞掉，大膽嘗試即可。

## 10. 發送紀錄與重送

路徑：左側選單 → **通知設定 → 發送紀錄**

- 上方統計卡顯示近 24 小時「已送出」「最終失敗」「待發送」「最舊待發（秒）」
- 下方清單可用狀態篩選（全部／已送出／失敗／最終失敗），每筆可看管道、標題摘要、狀態、嘗試次數
- 點 **詳情**（眼睛圖示）可看完整內文與投遞歷程（每次嘗試的時間、結果、失敗原因）
- `failed`（失敗待重試）會依系統排程自動重試；`dead`（最終失敗，已達重試上限）需要手動處理：
  - 單筆點 **重送**
  - 或右上角 **重送全部失敗**，一次重送當日所有最終失敗訊息

**狀態代碼對照**見 §13.2。

## 11. 收件人自助頁（給一般收件人）

這是給**收件人本人**使用的頁面，不是管理介面，不需要密碼登入——透過第 6.5 節產生的專屬連結進入。

收件人打開連結後可以：
- 查看自己目前的收件方式（Email／Telegram），調整發送模式（即時／每日摘要）、每日則數上限、靜音時段
- 在系統擁有者授權的範圍內，自行**收窄**（不能放寬）要接收的市場、訊號強度、訊號類型、策略分類
- 隨時「停止此管道」（等同取消訂閱該端點）

> 收件人在自助頁能調整的範圍，上限是系統擁有者在收件人頁面設定的「授權上限」；只有系統擁有者能放寬上限，收件人自己只能在上限內收窄，不能超出。

## 12. 常見問題與疑難排解

**Q1：訂閱規則、收件人、Telegram 都設定好了，但完全沒收到策略警示？**
依序檢查：
1. 管道狀態是否為「正常」（管道設定頁）
2. 該收件人的端點是否為「已驗證」（收件人頁面）
3. 是否有一條**啟用中**的訂閱規則、事件類型選對、過濾條件沒有意外濾掉這筆訊號（用「規則測試」驗證）
4. 到發送紀錄查該筆訊息的實際狀態——如果是 `digest_pending`（待摘要），代表被併入每日摘要而非即時發送，見 Q2

**Q2：為什麼訊息變成「待摘要」而不是立刻發送？**
策略警示訊號一律是一般（`info`）等級，若端點的發送模式是「每日摘要」或「僅緊急」，都會被併入下一次摘要（台股 15:00、美股 07:00 送出），不會遺失，只是延後。
- **個人**綁定的 Telegram 端點（第 6.3 節）預設就是「即時」，通常不用調整
- **群組（共用端點）**（第 7.2 節）預設是「僅緊急」，若想讓群組即時收到策略警示，需到收件人頁面找到該共用端點的偏好設定，把模式改成「即時」
- Email 端點預設是「每日摘要」（避免洗版信箱），如需即時信件可自行調整

**Q3：訊息顯示「延後」（deferred）？**
端點設定了靜音時段（預設 22:00–08:00），事件發生在靜音時段內就會延到靜音結束時間才送出。美股排程固定在台北時間 06:00 觸發，剛好落在預設靜音區間，該次警示會延到 08:00 才送出。如不想要這個延遲，可到端點偏好設定調整或清空靜音時段。

**Q4：訊息一直失敗，最後變成「最終失敗」？**
點該筆訊息「詳情」看投遞歷程的失敗原因，常見原因：
- Telegram：Bot Token 失效、收件人已封鎖機器人或解除綁定
- Email：SMTP 密碼錯誤、寄件配額用盡、收件信箱不存在
排除原因後可在發送紀錄手動「重送」。

**Q5：管道測試或某些頁面出現瀏覽器「CORS 被封鎖」錯誤？**
這通常不是真的跨網域設定問題，而是後端該次請求發生未預期例外，瀏覽器把找不到回應標頭的錯誤誤報成 CORS。請先查看後端終端機是否印出錯誤堆疊，多半是實際的伺服器端錯誤（500），而非 CORS 設定問題。

**Q6：改了後端程式碼，重新整理頁面卻沒有生效？**
確認後端是否確實重新啟動或熱重載成功（`reload=True` 在部分情況下不會即時偵測到變更）；不確定時直接停掉後端終端機重新執行 `python main.py` 最保險。

## 13. 附錄

### 13.1 事件類型一覽

| 代碼 | 顯示名稱 | 觸發時機 |
|---|---|---|
| `ALERT_SIGNAL` | 策略警示訊號 | 策略掃描（排程或手動觸發）命中訊號時，每筆訊號各一個事件 |
| `ALERT_DIGEST` | 每日警示摘要 | 系統內部摘要排程產生，不接受手動注入 |
| `FETCH_COMPLETED` | 每日抓取完成 | TWSE／yfinance 資料抓取完成後 |
| `FETCH_FAILED` | 抓取失敗 | 資料抓取發生錯誤時 |
| `SYSTEM_HEALTH` | 系統異常 | 系統健康檢查偵測到異常時 |

### 13.2 訊息狀態代碼一覽

| 代碼 | 顯示名稱 | 說明 |
|---|---|---|
| `pending` | 待發送 | 已排入佇列，等待下一次發送批次 |
| `sending` | 發送中 | 正在嘗試發送 |
| `sent` | 已送出 | 發送成功 |
| `failed` | 失敗待重試 | 發送失敗，系統會依重試策略自動再試 |
| `dead` | 最終失敗 | 已達重試上限，需手動重送 |
| `deferred` | 延後 | 命中靜音時段，延到時段結束後才送 |
| `digest_pending` | 待摘要 | 併入下一次每日摘要 |
| `digested` | 已併入摘要 | 已隨摘要送出 |
| `throttled` | 超量轉摘要 | 當日已達發送上限，改併入摘要 |
| `skipped_duplicate` | 重複略過 | 命中去重規則，同一事件對同一端點只送一次 |
| `skipped_paused` | 暫停略過 | 端點目前處於暫停狀態 |
