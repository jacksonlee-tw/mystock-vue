## 一、目的與範圍

### 1.1 需求來源

使用者需求（2026-08-29）：在熱力圖現有「依產業」分組之外，評估用「標籤」做股票的第二種分類（概念股，例如「CPO矽光子」「AI」「記憶體」），用於：

1. **分類排序功能**——依標籤分組顯示，並能排序（族群熱度排序＋群組內個股排序）。
2. **標籤篩選功能**——依標籤篩選熱力圖顯示的股票。
3. 其他優化建議。

### 1.2 交付範圍

| 項目 | 內容 |
|---|---|
| 資料模型 | 新增 `concept_tags.json`（per market），比照 `symbol_industry` 的 JSON-first 慣例，不建 Postgres 表（見 ADR-CT1） |
| 後端 | 新增 `GET /api/v1/stocks/concept-tags`，唯讀，寫法比照既有 `GET /stocks/industries` |
| 前端 | `HeatmapDashboard.vue` 新增：分類維度切換（依產業／依標籤）、標籤 `MultiSelect` 篩選（OR 語意）、標籤群組熱度排序、群組內個股排序下拉 |
| 標籤維護 | Phase 1 純手動編輯 JSON 種子檔（無管理 UI），驗證分類方式對使用者確實有幫助後，才評估 Phase 2 管理介面 |

### 1.3 不在本文件範圍

| 不做 | 原因 |
|---|---|
| 標籤管理 CRUD UI | Phase 1 先驗證分類/篩選是否有價值，避免一次把「建表 + CRUD API + 管理 UI」全部做掉，見 §八 |
| 涵蓋未追蹤股票 | 熱力圖本身只顯示 `get_target_stocks()` 範圍內的追蹤股票（見 §2.1），標籤範圍比照辦理；全市場涵蓋列入 §十一 後續延伸 |
| 策略選股池／通知訂閱整合 | 需同步改 `strategies/config_loader.py` 的 `scope` 語意，風險與效益需另外評估，列為 §十一 後續延伸 |
| 修復 `stocks.py` 既有路由回歸（§2.3） | 與本功能無強制依賴，屬前置技術債，建議另案處理，不併入本文件範圍 |

### 1.4 名詞定義

| 名詞 | 本文件定義 |
|---|---|
| **概念標籤（concept tag）** | 本文件新增的股票主題分類，多對多、非官方、需人工維護（例如「AI」「記憶體」「CPO矽光子」） |
| **產業分類（`symbol_industry`）** | 既有的官方 1:1 產業分類，TWSE/TPEx 自動抓取。與概念標籤是**兩層獨立的分類維度**，概念標籤不取代產業分類 |
| **觀察名單標籤（`watchlist_tag`）** | 既有的個人整理標籤（例如「存股」「短線」），掛在 `portfolio_watchlist` 項目上。與概念標籤語意不同、字典表不共用（見 ADR-CT1） |
| **產業鏈關聯（`industry_chain_edges`）** | 規劃中、**尚未落地**的個股對個股有方向性關聯（供應鏈）。與概念標籤不同層次，不在本文件範圍 |

## 二、現況盤點

### 2.1 熱力圖現況

- **資料範圍**：`GET /api/v1/stocks/heatmap` → `get_heatmap_data()`（`backend/services/stock_service.py:126-143`）只回傳 `get_target_stocks(market)`（`.env` 的 `STOCK_CODES`/`US_STOCK_CODES`）範圍內的股票，**不是全市場**。個人追蹤清單通常是幾十檔等級（`frontend/src/views/HeatmapDashboard.vue:187` 註解：「個人自選股清單通常每個產業只有 1~2 檔」）。這對「人工維護概念股標籤」是好消息：工作量可控。追蹤清單的範圍本身另有規劃中的擴充（持股自動納入追蹤，見 `docs/15.追蹤個股清單優化/追蹤與觀察名單整合_規劃書.md` §12），與本文件無關——不論範圍多大，本文件的分類/篩選/排序設計都直接適用。
- **現有分類邏輯**（`HeatmapDashboard.vue:194-233`）：指數 → ETF → 依 `symbol_industry` 分組，不足 3 檔的產業合併成「其他個股」並掛 `industry_tag` 徽章。**只有查無產業資料時才會退回「指數/ETF/一般個股」三分類**——這個三分類其實是 fallback，正常情況下已經有一層產業分組。概念標籤的定位是**在「依產業」之外再加一種分類維度**，不取代現有邏輯。
- **排序**：目前完全沒有排序控制——卡片依 API 回傳順序（股票代號），分類群組之間也沒有「熱度」排序。這是與標籤功能無關、但同樣值得補的缺口（見 §六）。

### 2.2 系統既有「分類/標籤」機制盤點

| 機制 | 粒度 | 資料來源 | 目前用途 | 關鍵檔案 |
|---|---|---|---|---|
| `symbol_industry` | 個股 → 單一產業（**1:1**） | TWSE/TPEx 官方分類，`services/industry_fetcher.py` 自動抓 | 熱力圖分組、規劃中的投組圓餅圖 | `db/migration/V6__*.sql`、`V7__*.sql`、`HeatmapDashboard.vue` |
| `watchlist_tag` / `watchlist_item_tag` | 觀察名單項目 → 多標籤（**多對多**） | 使用者手動建立（例如「存股」「短線」） | 觀察名單頁篩選/整理 | `db/migration/V12__Extend_watchlist_tracking.sql`、`views/portfolio/WatchlistView.vue`、`composables/useWatchlistTags.js` |
| `industry_chain_edges` | 個股 → 個股，**有方向性** | 規劃中，**尚未落地**（無 migration、無 module） | 產業鏈供應關係／補漲名單 | 僅設計文件 `docs/16.AI技術分析/Phase3-產業鏈知識圖譜與輪動模型.md` |
| 類股指數輪動 | 類股指數層級 | 官方類股指數 | 產業輪動排行 | `views/SectorRotationView.vue` |
| **概念標籤（本文件）** | 個股 → 多主題（**多對多**） | **無官方來源，人工維護** | 熱力圖分類排序／篩選 | 新增，見 §四、§五 |

`docs/16.AI技術分析/Phase3-產業鏈知識圖譜與輪動模型.md` §2.1 在引入「產業鏈關聯」時，特地寫了一張表警告「必須在文件與 UI 用語上明確區分，否則會讓使用者誤以為是重複功能」——本文件延續同一慣例，§1.4 的名詞定義即為此設計。

### 2.3 盤點過程中發現的既有問題（與本功能相關，供排優先序）

`backend/api/v1/endpoints/stocks.py` 目前**缺少** `GET /symbols`、`/symbols/industry-options`、`/symbols/sync`、`/industries/sync`、`/{stock_id}/vs-index` 路由（連帶 `repositories/stock_repository.py` 的對應查詢函式也一起消失）。追出來是 commit `27a7f96`（左邊menu功能tree調整）夾帶了大量檔案的還原/刪減，但前端 `views/StockSymbolBrowser.vue`（選單「全市場代碼查詢」，路由 `/stocks/symbols`，選單項仍在）跟 `service/stockApi.js` 沒有跟著拿掉，目前這頁會直接打 404、顯示空表格。

這頁本來是「批次幫股票掛標籤」最合適的地方——已有分頁表格＋篩選＋單筆「加入追蹤」的雛形，只要加一個批次動作就能變成標籤管理 UI（§十一 Phase 2）。**建議在啟動 Phase 2（管理 UI）之前先修掉這個回歸**，本文件 Phase 1（§八）不依賴它，故不影響本功能起步。

## 三、設計決策（ADR）

### ADR-CT1：資料模型採 JSON 檔案，不建 Postgres 表

**決策**：新增 `data/{market}/_meta/concept_tags.json`，比照既有 `symbol_industry` 的 JSON 鏡像模式（`/stocks/industries` → `load_industries_json()`，`api/v1/endpoints/stocks.py:58-61`），**不新增 Postgres migration**。

評估過的三個方案：

| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **A. JSON 檔案（採用）** | `concept_tags.json`：tag 字典（名稱/顏色）+ symbol↔tag 多對多對照，對稱新增 `GET /stocks/concept-tags` | 不受 `DATA_SOURCE` 開關影響，JSON／Postgres 部署皆可用；不需 migration；維護方式與 `industries.json` 一致 | 沒有資料庫層級查詢/索引（以幾十檔追蹤股票規模，非問題） |
| B. 仿 `watchlist_tag` 建獨立 Postgres 表（`concept_tag`/`concept_tag_symbol`） | 新 migration + CRUD API + 新 composable | 語意最乾淨，日後最好擴充到「未追蹤股票」也能標記 | 需要 Postgres，開發量明顯較大；本次 Phase 1 目標是低成本驗證，暫不需要 |
| C. 直接重用既有 `watchlist_tag` | 概念主題塞進同一標籤字典 | 開發成本最低，UI 元件現成 | **資料對不齊風險**：`get_target_stocks()`（`config.py:39-48`）直接讀 `.env`，跟 `portfolio_watchlist` 無強制關聯，只有「跑 Postgres + 追蹤清單已整合進 `portfolio_watchlist`」的部署下標籤涵蓋範圍才會對得起來；且個人整理標籤與主題標籤混在同一字典，UI 難以分辨用途 |

**理由**：本專案「熱力圖用的靜態分類中繼資料」已有明確慣例（`symbol_industry` 走 JSON），採用同一慣例成本最低、風險最小。若未來需求擴大到「全市場都要能標記」（超出追蹤清單範圍），屆時再评估升級為方案 B（見 §十、§十一）。

**代價與對策**：JSON 檔案沒有 DB 層級的唯一性/外鍵約束，需在讀取時（§五）自行驗證格式並優雅降級（tag id 重複、symbol 對應到不存在的 tag id 時忽略該筆並記警告，不讓整支 API 掛掉）。

### ADR-CT2：概念標籤與產業分類是獨立維度，不合併顯示邏輯

**決策**：`HeatmapDashboard.vue` 新增「依標籤」分組為**獨立的 computed 分支**，不與現有 `generalStocksByIndustry`（`HeatmapDashboard.vue:169-185`）共用邏輯或互相依賴。使用者在「依產業」／「依標籤」間切換，兩者資料各自獨立抓取、獨立渲染。

**理由**：兩者本質不同——產業分類是互斥的（一檔股票一個產業），概念標籤是非互斥的（一檔股票可能同時屬於多個標籤，同一張卡片會出現在多個標籤群組）。若強行合併成同一份 `categories` computed，會讓「一檔股票在畫面上出現兩次」這種**刻意的重複顯示**跟既有「不足 3 檔合併其他個股」的**去重合併**邏輯混在一起，難以維護與說明。

### ADR-CT3：標籤篩選採 OR 語意

**決策**：熱力圖的標籤篩選（勾選多個標籤時）採 **OR 語意**——顯示「符合任一勾選標籤」的股票。

**理由**：概念股篩選的直覺用法是「看 AI 或 記憶體相關的股票有哪些」，而非「同時符合 AI 且記憶體」（後者交集通常很小甚至是空集合）。這與既有 `WatchlistView.vue` 的標籤篩選（`portfolioApi.getWatchlist({ tags })`，AND 語意）**刻意不同**——UI 文案必須明確標示（例如篩選元件旁加一行「符合任一標籤」提示），避免使用者誤套用觀察名單頁的既有心智模型。

### ADR-CT4：Phase 1 不做管理 UI，標籤資料由人工維護 JSON 種子檔

**決策**：Phase 1（見 §八）只做「讀取＋分組＋篩選＋排序」，標籤字典與對照表由人工直接編輯 `concept_tags.json`，不提供任何前端管理介面。

**理由**：概念標籤沒有官方資料源，價值需要先被使用者驗證（分類方式是否真的有幫助、OR 篩選語意是否符合直覺），再決定要不要投入管理 UI 的開發成本。這與 `strategy_config/strategies.yaml`（人工編輯 YAML 調策略門檻，不做管理介面）是同一種務實作法。

## 四、資料模型

`data/{market}/_meta/concept_tags.json`（例如 `data/tw/_meta/concept_tags.json`）：

```json
{
  "tags": [
    { "id": "ai", "name": "AI", "color": "amber", "sort_order": 1 },
    { "id": "cpo-photonics", "name": "CPO矽光子", "color": "violet", "sort_order": 2 },
    { "id": "memory", "name": "記憶體", "color": "sky", "sort_order": 3 }
  ],
  "symbol_tags": {
    "2330": ["ai"],
    "3661": ["cpo-photonics", "ai"],
    "2408": ["memory"]
  }
}
```

- `tags[].id`：穩定的英數 slug，作為 `symbol_tags` 對照 key 與篩選 value，**不隨顯示名稱改變**（改名只需改 `name`，不影響既有對照關係）。
- `tags[].color`：直接沿用 `useWatchlistTags.js:11-18` 既有的 6 色 Tailwind 色票 key（`slate/violet/amber/emerald/rose/sky`），前端可共用同一份 `TAG_COLOR_CLASSES`/`tagColorClass()`，不用另建一套色彩系統。
- `symbol_tags`：`{ symbol: [tag_id, ...] }`，一檔股票可對應 0~N 個標籤；查無標籤的股票不出現在此物件中（不需要顯式空陣列）。
- 與 `industries.json`（`{symbol: {industry_code, industry_name}}`）的結構差異：`industries.json` 是 1:1 所以直接攤平；`concept_tags.json` 是多對多，需要 `tags` 字典 + `symbol_tags` 對照表兩段式結構，並讓 `tags[].id` 同時具備「唯一鍵」與「篩選 value」兩種角色，避免前端還要另外查一次名稱。

## 六、前端規格

`frontend/src/views/HeatmapDashboard.vue` 異動點：

1. **資料載入**：新增 `conceptTags = ref({ tags: [], symbol_tags: {} })`，比照既有 `loadIndustries()`（`HeatmapDashboard.vue:300-307`）的失敗降級慣例（讀取失敗只讓「依標籤」分組不可用，不影響熱力圖本體），新增 `loadConceptTags()` 並在 `onMounted` / `watch(currentMarket)` 一併呼叫。`stockApi.js` 新增 `getConceptTags(market)`，寫法比照既有 `getIndustries(market)`。
2. **分類維度切換**：標題列旁新增「依產業」／「依標籤」切換鈕（沿用既有週期切換鈕的按鈕群組樣式，`HeatmapDashboard.vue:18-33`）。`groupBy = ref('industry')`，`categories` computed 依 `groupBy` 值回傳 `generalStocksByIndustry`（既有）或新的 `stocksByConceptTag`（新增，依 ADR-CT2 獨立實作，因為同一檔股票會依標籤數量重複出現在多個群組，不能重用「不足 3 檔合併」的去重邏輯）。
3. **標籤篩選**：比照 `WatchlistView.vue` 現成 pattern：`<MultiSelect v-model="tagFilter" :options="conceptTags.tags" optionLabel="name" optionValue="id" display="chip" placeholder="篩選標籤（符合任一即顯示）" />`，放在分類維度切換鈕旁。篩選邏輯依 ADR-CT3 為 OR 語意，套用在 `stocks` 上游（產業分組與標籤分組畫面都會反映篩選結果）。
4. **卡片標籤徽章**：現有 `stock.industry_tag` 徽章（`HeatmapDashboard.vue:80-85`）旁新增渲染該股票的概念標籤 chip（用 §四 `symbol_tags[stock.stock_id]` 對應到 `tags[].name`/`color`），色彩沿用 `useWatchlistTags.js` 的 `tagColorClass()`。
5. **群組層級排序**（`groupBy === 'concept'` 時）：`stocksByConceptTag` 依各群組股票的平均 `change_percent` 由高到低排序，漲最多的主題排最前面。
6. **個股層級排序**（不限標籤功能，見 §七）：每個分類/標籤區塊新增排序下拉（漲跌幅／成交量／代號），比照 `MarketScreener.vue` 既有排序慣例，作用在區塊內的 `stocks` 陣列。

## 七、其他優化建議

以下項目不是本功能的必要前提，但盤點過程中一併發現、與熱力圖／分類體驗直接相關，建議一併考慮：

1. **修復 §2.3 的路由回歸**——`StockSymbolBrowser.vue` 現在對使用者來說是一個會報 404 的空白頁，也是未來標籤管理 UI（Phase 2）最合適的落點，建議在啟動 Phase 2 前處理。
2. **統一 ETF 判斷邏輯**：前端 `isEtf()`（`HeatmapDashboard.vue:223-233`，寬鬆版 `startsWith('00')`）與後端 `_CHIP_EXCLUDED_SYMBOL_PATTERN`（`strategies/scanner.py:69`，較嚴謹的正規表示式）是兩份獨立、邏輯不完全一致的實作，建議抽成共用工具或至少讓兩邊算式一致。
3. **分類/篩選/排序狀態記憶**：比照 `useMarket()` 的 singleton + `localStorage` pattern（`composables/useMarket.js`），把使用者選的 `groupBy`/`tagFilter`/排序方式記住，切換市場或重整頁面不會被重置——與 `CLAUDE.md` 既有「切換圖表不能整頁 refresh 跳回最上方」規則同屬一種使用者體驗要求，建議一併遵守。

## 九、驗收條件

- 熱力圖可在「依產業」／「依標籤」間切換，且不影響既有依產業分組行為（回歸測試）。
- 標籤篩選為 OR 語意：勾選多個標籤時顯示符合任一標籤的股票；清空篩選回復顯示全部。
- 依標籤分組時，群組依平均漲跌幅由高到低排序。
- 每個分類/標籤區塊內的個股排序下拉可正常切換（漲跌幅／成交量／代號）。
- `concept_tags.json` 不存在、格式錯誤，或 `market` 沒有對應檔案時，優雅退回「無標籤分組可用」（比照 `industries` 缺資料時的既有 fallback 慣例），不影響熱力圖本體與「依產業」分組。
- `npm run build` 通過。
