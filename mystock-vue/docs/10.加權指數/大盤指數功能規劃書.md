## 一、簡介與目標

### 1.1 目標

讓使用者在既有的個股／籌碼分析之外，能夠：

1. **掌握市場全貌**——一眼看到台股與美股主要指數的最新表現。
2. **判讀市場內部結構**——不只看指數點數，還能看漲跌家數、資金流向、類股輪動等「大盤的體質」。
3. **評估相對強弱**——把個股與投資組合放到大盤這把尺上量，回答「我贏大盤了嗎」。
4. **在大盤轉折時被主動告知**——沿用既有警示引擎與通知平台，不另建一套。

### 1.2 支援指數範圍

| 階段 | 市場 | 指數 | 系統代號 | 外部代號 | 說明 |
|---|---|---|---|---|---|
| P1 | tw | 發行量加權股價指數 (TAIEX) | `TWII` | `^TWII` | 台股核心指標 |
| P1 | us | 道瓊工業指數 | `DJI` | `^DJI` | 藍籌股 |
| P1 | us | 標普 500 指數 | `GSPC` | `^GSPC` | 大型股綜合 |
| P1 | us | 那斯達克綜合指數 | `IXIC` | `^IXIC` | 科技股 |
| P1 | us | 費城半導體指數 | `SOX` | `^SOX` | 半導體，與台股連動最深 |
| P2 | tw | 櫃買指數 (OTC) | `TWOII` | `^TWOII` | 中小型股風向，台股使用者高頻查看 |
| P2 | tw | 未含金融保險股指數 | `TWII_XF` | — | TWSE MI_INDEX 提供 |
| P2 | tw | 未含電子股指數 | `TWII_XE` | — | 判斷是否「電子撐盤」 |
| P2 | tw | 台股 28 類股指數（電子、金融、航運…） | `TWSE_S{代碼}` | — | 類股輪動分析用（見 §5.5） |
| P2 | us | 恐慌指數 VIX | `VIX` | `^VIX` | 市場風險情緒 |
| P3 | us | 美股 11 大 GICS 類股 ETF 代理（XLK/XLF/XLE…） | 各自代號 | 同名 | 以 ETF 代理類股指數（見 §8.2） |

> **代號設計**：系統內一律使用**不含 `^` 的系統代號**（`TWII`、`DJI`…），
> 外部代號 (`^TWII`) 只存在於 fetcher 與資料來源設定中。
> 理由：`^` 在 URL path 需編碼為 `%5E`，在檔名與 Docker volume 掛載上也易生歧義；
> 而 `symbols.symbol` 是 `String(20)` 主鍵（見 `backend/db/models.py`），系統代號可直接沿用。

### 1.3 設計原則（貫穿全文）

| 原則 | 說明 |
|---|---|
| **P-1 不另建平行系統** | 指數是「另一種標的」，不是「另一套資料流」。能複用 `stock_service` / `StockCharts.vue` 的一律複用。 |
| **P-2 顯示能力由設定驅動** | 指數要顯示哪些面板，由 `MarketAdapter.meta.panels` / `metrics` 決定，不在元件裡寫 `if (isIndex)`。 |
| **P-3 雙資料源對等** | JSON（預設）與 PostgreSQL 兩條路徑都要能跑，讀取分歧只准出現在 `load_stock_data()`。 |
| **P-4 誠實標示資料缺口** | 抓不到的欄位顯示「—」，不補 0（沿用 `db/mapping.py` 第 99 行的既有約定）。 |
| **P-5 日線優先** | Phase 1~3 全部建立在日線收盤資料上；盤中即時是獨立階段（見 ADR-I8）。 |

## 二、與現有架構的整合決策（ADR）

> 這一節是本文件最關鍵的部分。v1.0 的規劃把指數當成全新的子系統（新資料表、新 Model、新 API、Celery 任務），
> 實際上本專案已有的多市場抽象、雙資料源、圖表舞台、警示引擎都可以直接承接指數。
> 以下決策的目的是**把新增程式碼量壓到最低，同時不破壞既有約定**。

### ADR-I1：指數即標的（Index-as-Symbol）

**決策**：指數登記在既有的 `symbols` 表（或 JSON 對應目錄），以 `security_type = 'index'` 區分，
每日資料寫入既有的 `daily_stock_data`（`open/high/low/close/volume/turnover`）。
**不新增 `market_indices` 資料表。**

**理由**：
- 指數的核心資料就是 OHLCV，與個股同構；新建表等於把 `aggregate_stock_data()`、`compute_ma_set()`、
  `get_stock_chart_payload()`、K 線元件全部再實作一次。
- `daily_stock_data.market_specific_data` 是 JSONB（`backend/db/models.py:53`），
  台股大盤專屬欄位（漲跌家數、委買委賣、未含金融指數…）直接放進去，
  **儲存層零 schema 變更**，不需要新的 Flyway migration。

**代價與對策**：
- `daily_row_to_record()`（`backend/db/mapping.py:93`）需新增 `index_stats` 區塊的還原邏輯，
  `_build_market_specific_data()` 需新增對應的寫入分支。兩個方向必須同時改（該檔案開頭已有此警告）。

### ADR-I2：讀取一律走 `load_stock_data()`

**決策**：指數的讀取不得新增 `get_data_source()` 分支。
`services/stock_service.py` 的 `load_stock_data()` 是唯一允許判斷 JSON/Postgres 的地方（CLAUDE.md 明列）。
指數只需擴充該函式的**路徑解析**（JSON 子目錄），不擴充其分支邏輯。

### ADR-I3：指數不得污染個股清單與熱力圖

**決策**：指數不出現在個股下拉選單、熱力圖、追蹤清單中。

**實作要點（已驗證的整合縫隙）**：

| 位置 | 現況 | 指數導入後 |
|---|---|---|
| `_list_stock_ids_json()` (`stock_service.py:37`) | 只收 `.json` 檔、跳過 `_` 開頭 | 指數存 `data/{market}/_indices/*.json`，**子目錄天然被略過**，零修改 |
| `_list_stock_ids_db()` → `StockRepository.list_symbols()` (`stock_repository.py:90`) | 無 `security_type` 過濾 | **需新增 `security_type` 過濾參數**，並讓 `discover_available_stocks()` 排除 `index` |
| `get_heatmap_data()` (`stock_service.py:118`) | 以 `get_target_stocks()` 白名單過濾 | 指數不寫進 `STOCK_CODES`，天然排除，零修改 |
| `stock_json_path()` (`fetcher.py:115`) | `data/{market}/{id}.json` | 需新增 `kind='index'` 參數以指向 `_indices/` 子目錄 |

### ADR-I4：顯示面板由 MarketAdapter 驅動

**決策**：新增 `panels` 值 `index`、`breadth`、`sector`，以及對應的 `Metric` 定義，
掛在 `markets/tw.py` / `markets/us.py` 的 adapter 上（`backend/markets/base.py` 的 `MarketMeta` / `Metric`）。
前端 `StockCharts.vue` 的 `widgetDefinitions`（第 121 行）以 `panel` 欄位過濾，
新增指數專屬 widget 時只加陣列項目，不加條件判斷。

**理由**：台股大盤有漲跌家數、委買委賣、大盤法人；美股指數沒有（yfinance 不提供市場寬度）。
這正是 `panels` 機制設計的用途，不該退化成 `if (market === 'tw' && isIndex)`。

### ADR-I5：漲跌配色沿用市場慣例，不為指數另訂

**決策**：指數卡片與 K 線一律透過 `frontend/src/utils/marketColors.js` 的
`getUpDownColor(market)` 取色 —— 台股紅漲綠跌、美股綠漲紅跌。

> ⚠️ **修正 v1.0**：v1.0 寫「參考原圖為綠漲紅跌」，這與本系統既有的台股慣例（`up_down_convention: 'red_up'`，
> 見 `markets/tw.py:44`）直接衝突。若照 v1.0 實作，同一頁的大盤卡片與個股 KPI 卡會出現相反配色。
> 配色一律以 adapter 的 `up_down_convention` 為準。

### ADR-I6：排程沿用 APScheduler，不引入 Celery

**決策**：指數抓取掛在 `services/scheduler.py` 既有的市場抓取 job 之後（與 `_scan_after_fetch()` 同一串鏈）。

> ⚠️ **修正 v1.0**：v1.0 標題寫「任務排程 (Celery / Background Tasks)」，
> 但本專案使用 `AsyncIOScheduler`，且時間可由 `PUT /api/v1/schedule` 熱套用（`scheduler.py:269`）。
> 引入 Celery 需要額外的 broker 容器，與現行「scheduler 跑在 uvicorn 程序內、無獨立 worker」的部署假設相斥。

**串接方式**：在 `_run_if_idle()` 中，於 `fetch_fn()` 之後、`_scan_after_fetch()` 之前插入 `_fetch_indices(market)`，
使指數資料在策略掃描前就位（大盤警示策略才掃得到當日資料）。

### ADR-I7：指數警示走既有警示引擎，不另寫判斷

**決策**：大盤警示（跌破年線、單日重挫）以 `strategy_config/strategies.yaml` 的策略定義表達，
掃描時把指數代號當成 symbol 傳進 `scan_market(market, symbols=[...])`（`scanner.py` 已支援 `symbols` 參數）。
去重、Cooldown、強度分級、通知發佈（`_publish_after_scan()`）全部免費繼承。

**必要的新增**：
- 新條件型別 `daily_change_pct`（單日漲跌幅門檻），放在新檔 `strategies/conditions_index.py`，
  **並且必須在 `strategies/__init__.py` 加一行 import**，否則 `@condition` 裝飾器不會註冊（該檔案開頭已有此註記）。
- 籌碼類策略需排除指數：`scanner.py:49` 的 `_CHIP_EXCLUDED_SYMBOL_PATTERN` 目前只排除台股 ETF（`00` 開頭），
  指數代號（`TWII`）不符該樣式，會被籌碼策略掃到。應改為「`security_type == 'index'` 或符合 ETF 樣式」即排除。

### ADR-I8：日線優先，盤中走勢獨立階段

**決策**：Phase 1~3 的所有指數功能建立在**日線收盤資料**上。
卡片的 Sparkline 在 Phase 1 顯示「近 20 個交易日收盤走勢」，
Phase 4 才替換為「當日盤中走勢（昨收基準線）」。

**理由（誠實的範圍評估）**：v1.0 要求的「當日 Sparkline，以昨收為基準線、上下雙色漸層」需要**分鐘級資料**，
而本系統目前**完全沒有盤中資料管線**——排程一天只跑一次（台股 14:30 / 美股 06:00），
儲存結構以 `YYYY-MM-DD` 為鍵、一天一筆。要支援盤中需要：新的時間序列儲存、新的抓取頻率
（盤中每 N 分鐘）、`session_state()` 判斷（`markets/tw.py:83` 目前**寫死回傳 `closed`**，需先補完）、
以及對免費 API 的 rate limit 評估。這是獨立的工程項目，不應綁在 Phase 1 的交付範圍裡。

## 三、資料獲取與更新

### 3.1 台股資料來源（TWSE）

現有 `services/fetcher.py` 已在使用 TWSE `rwd` 系列 API（`STOCK_DAY`、`MI_MARGN`、`T86`），
指數資料沿用同一套 `requests` + 節流慣例（含 `time.sleep` 間隔、失敗重試）。

| 用途 | 端點 | 提供欄位 | 對應顯示功能 |
|---|---|---|---|
| 大盤日 OHLC | `rwd/zh/indicesReport/MI_5MINS_HIST` | 加權指數 開/高/低/收（月表） | FR-IDX-03 K 線 |
| 大盤成交統計 | `rwd/zh/afterTrading/FMTQIK` | 成交股數／金額／筆數、加權指數、漲跌點數（月表） | FR-IDX-04 量能 |
| 每日收盤行情 | `rwd/zh/afterTrading/MI_INDEX` | 漲跌證券數合計、各類指數收盤、委買委賣筆數/張數 | FR-IDX-10~13、FR-IDX-30 |
| 各類股成交量值 | `rwd/zh/afterTrading/BFIAMU` | 各類股成交股數/金額/筆數 | FR-IDX-22 資金流向 |
| 大盤三大法人 | `rwd/zh/fund/BFI82U` | 三大法人買進/賣出/買賣差額（金額） | FR-IDX-20 |
| 大盤信用交易 | `rwd/zh/marginTrading/MI_MARGN` | 融資融券總計（**現有程式已在抓，取其總計列即可**） | FR-IDX-21 |
| 大盤估值 | `rwd/zh/afterTrading/BWIBBU_d`（待驗證） | 本益比／殖利率／股價淨值比 | FR-IDX-41 |
| 櫃買指數 | TPEx OpenAPI（P2，待驗證） | OTC 指數 OHLC | §1.2 P2 |

> ⚠️ **實作前必做**：上述端點的實際路徑、參數名與回傳 `fields`/`data` 結構**必須逐一實測驗證**
> （TWSE 曾多次調整 `rwd` 路徑與欄位順序）。建議先寫一支 `backend/scripts/probe_index_sources.py`
> 逐端點打一次、把回傳結構 dump 成 JSON 存檔，作為欄位對照表（附錄 A）的實證依據，再開始寫 fetcher。

### 3.2 美股資料來源（yfinance）

`services/us_fetcher.py` 與 `markets/us.py` 已使用 `yfinance`，指數只是換代號（`^DJI` 等），
`ticker.history()` 直接可用，**無需新增第三方套件**。

注意事項：
- 指數的 `Volume` 欄位常為 0 或不具意義（尤其 `^DJI`、`^SOX`），量能圖對美股指數應**隱藏**而非顯示 0（原則 P-4）。
- `ticker.info` 對指數多半缺 `shortName` 以外的欄位；`validate_symbols()` 的既有流程可用，但不應期待取得 short interest / holders。
- yfinance 亦可作為**台股指數的 fallback**（`^TWII`），在 TWSE 端點異常時降級使用（見 3.4）。

### 3.3 抓取模式與排程

| 項目 | 設計 |
|---|---|
| 歷史初始化 | 新增 `backend/scripts/init_index_history.py`，一次性回補 N 年日線（預設 5 年，`--years` 可調），**冪等**（比照 `scripts/import_json_to_postgres.py` 慣例）。 |
| 每日更新 | 掛在 `services/scheduler.py` 既有市場 job 內，順序：**個股抓取 → 指數抓取 → 策略掃描 → 通知發佈**。 |
| 手動觸發 | `POST /api/v1/indices/sync`；沿用 `fetch_status` 單例的 in-flight 互斥（`fetcher.py:89`），避免與個股抓取搶 TWSE 額度。 |
| 抓取模式 | 沿用既有 `incremental`（補最後一筆之後的缺口）／`repair`（完整區間重抓）語意。 |

### 3.4 錯誤處理與降級

1. **重試**：沿用 fetcher 既有的重試與節流慣例，不另立機制。
2. **降級**：台股指數優先 TWSE；連續失敗時改用 yfinance `^TWII` 取 OHLC（僅 OHLC，市場寬度欄位不可得，該日對應面板顯示「—」）。
3. **通知**：抓取失敗沿用 `_publish_fetch_result()`（`scheduler.py:66`）發 `FETCH_FAILED` 事件，
   **不需要在指數模組裡 import notify 任何東西**（通知平台鐵則 R1：只有 scheduler 是接縫）。
4. **絕不寫 0**：指數 OHLC 抓不到時**不落檔**，而不是寫 0.0。
   `scripts/restore_price_from_legacy.py` 記錄了個股曾因「抓不到寫 0」造成的歷史修復成本，指數不重蹈覆轍。

## 四、資料儲存與模型設計

### 4.1 標的註冊

指數以 `security_type='index'` 註冊於 `symbols`（Postgres）或設定檔（JSON 模式）。
建議新增 `backend/config/indices.yaml`（或沿用 `strategy_config/` 的擺法）集中定義：

```yaml
# 指數定義：新增指數 = 加一筆設定，不改程式碼（比照 strategies.yaml 的設計精神）
indices:
  - code: TWII                 # 系統代號（symbols.symbol）
    market: tw
    name: 發行量加權股價指數
    short_name: 加權指數
    source:
      primary: twse            # twse | yfinance
      fallback: yfinance
      external_symbol: ^TWII
    panels: [index, breadth, sector, institutional_market, margin_market]
    display_order: 1
    default_tab: true          # 首頁市場總覽預設顯示
  - code: SOX
    market: us
    name: 費城半導體指數
    source: { primary: yfinance, external_symbol: ^SOX }
    panels: [index]
    display_order: 4
```

### 4.2 每日資料欄位

**通用欄位（沿用 `daily_stock_data` 既有欄位，零變更）**

| JSON 鍵 | DB 欄位 | 說明 |
|---|---|---|
| `open` / `high` / `low` / `close` | `open_price` / … / `close_price` | 指數點數 |
| `volume` | `volume` | 成交股數（美股指數多半無意義，見 3.2） |
| `amount` | `turnover` | 成交金額（台股常用「億元」呈現，換算在前端做） |
| `trades` | `transaction_count` | 成交筆數 |

- **`daily_stock_data`：無需 migration**（`market_specific_data` JSONB 已足夠）。

## 六、與個股／投資組合的對比分析

| ID | 功能 | 說明 | 依賴 |

| FR-IDX-50 | **個股 vs 大盤疊圖** | 在個股 K 線頁新增一個 widget：個股與所屬市場指數 Rebase=100 疊圖，另附 RS 相對強弱線（個股報酬 − 指數報酬） | 指數日線；日期對齊採 §4.5 |
| FR-IDX-51 | **投資組合 vs 大盤** | 投資組合淨值曲線與指數疊圖，計算 **Alpha**（超額報酬）、**Beta**（波動相關性）、**追蹤誤差** | ⚠️ **依賴個人投資記帳功能**（`docs/8.個人投資記帳功能/`），該模組目前**僅有設計文件、尚未實作**。本項排入 Phase 3 且以該模組完成為前提 |

**Beta / Alpha 計算約定**（避免各處算法不一）：
- 以**日報酬率**計算，預設回看窗 60 個交易日（可設定）。
- Beta = Cov(組合報酬, 指數報酬) / Var(指數報酬)。
- Alpha 採 Jensen's Alpha，無風險利率預設 0（可於 `.env` 設定），並在 UI 明確標示此假設。
- 計算實作放 `backend/indicators/`（與 `moving_average.py`、`chip.py` 同層），**由後端統一計算**，
  比照均線的既有決策——避免前後端各算一次而數字對不上。

| 站上年線 | 收盤突破 MA240 | `info` |

| 騰落線背離 | 指數創高、ADL 未創高（P2） | `warning` |
| VIX 飆升 | VIX 單日 +20% 或突破 30（P2） | `warning` |

## 八、產業與類股分類

> ⚠️ **v1.0 的概念混淆**：v1.0 把「類股指數」與「個股產業標籤」寫在同一節。
> 兩者資料來源、儲存方式、用途都不同，必須拆開，否則實作時會做出一個既非指數又非標籤的四不像。

### 8.1 類股指數（屬於本指數功能）

如 §5.1-D 所述，類股指數就是指數，以 ADR-I1 的方式儲存與呈現，**不需要額外機制**。

### 8.2 個股產業標籤（獨立子功能）

| 項目 | 設計 |
|---|---|
| 目的 | 讓個股知道自己屬於哪個產業，才能做「投資組合產業配置圓餅圖」與「同業比較」 |
| 台股來源 | TWSE 上市公司基本資料／ISIN 分類（一次性抓取 + 季度更新即可，非每日） |
| 美股來源 | yfinance `ticker.info` 的 `sector` / `industry`（GICS 近似），抓取時順手取得 |
| 儲存 | 新表 `symbol_industry`（migration **V6**）：`symbol` / `market_type` / `sector_code` / `sector_name` / `industry_name` / `updated_at`；JSON 模式對應 `data/{market}/_meta/industries.json` |
| 用途 | ①投資組合產業配置圓餅圖 ②熱力圖依產業分組（現行 `HeatmapDashboard.vue` 只有「ETF／一般個股」兩組，可升級為產業分組）③同業相對強弱 |
| 階段 | Phase 3（不阻擋指數核心功能） |
