## 0. 這份文件在講什麼

Phase 5 原始草稿（本文件的前一版）把「單股 AI 診股報告」的整套機制——多模態截圖、雙引擎
Provider、結構化輸出、歷史落地、FastAPI 路由、Vue 彈窗——當作**尚待開發**的清單列出。但目前
分支（`feature/message-plateform`）上這一套已經**依 [AI技術分析規劃.md](AI技術分析規劃.md)
完整實作並可用**（見第 1 節）。繼續把它們列為「Phase 5 待做」只會誤導後續開發，因此本次改版：

1. 先盤點「已完成」與程式碼的對應關係，避免重工。
2. 把 Phase 5 真正還沒做、且原始草稿的核心訴求（三層式 Context、戰情室彙總視圖、推播整合）
   收斂成具體的**功能需求**（FR），每項附驗收標準與相依關係。
3. 明確排除的項目、待決策的開放問題，都列出來，不留在正文裡混著講。

本文件是**功能需求文件**（What／Why），不是技術設計規格書（How）。真要動工前，比照
[AI技術分析規劃.md](AI技術分析規劃.md) 的先例，各 FR 應個別展開成有 ADR、資料庫設計、API
設計的規格書再開發；本次僅寫文件，不產出任何程式碼。

## 2. Phase 5 正式版目標

在已完成的單股技術面診股報告之上，把 Phase 1～4 已經產出的籌碼、基本面、（未來的）產業鏈與

一致。

## 4. 功能需求

### FR-5.1　三層式 Context 擴充引擎（新增基本面層）

**需求描述**：`ai/summary.py` 的 Context 組裝，在既有技術面／籌碼面之外，加入第三層基本面
數據：最新月營收 YoY／MoM、最近一季 EPS 年增率、本益比（P/E）、股價淨值比（P/B）、現金殖利率。

**資料來源**：全部是既有資料，不需新爬蟲——

- 月營收／EPS：[services/mops_fetcher.py](../../backend/services/mops_fetcher.py)、
  [services/mops_eps_fetcher.py](../../backend/services/mops_eps_fetcher.py) 已抓取的資料，
  經 [api/v1/endpoints/fundamentals.py](../../backend/api/v1/endpoints/fundamentals.py) 暴露。
- 估值（P/E／P/B／殖利率）：[services/valuation_fetcher.py](../../backend/services/valuation_fetcher.py)
  已正規化的每日快照。
- `fundamentals.py` 的 `/compare` 端點已示範如何用 `MarketPreload` 批次組裝行情＋估值＋營收，
  `ai/summary.py` 應比照同一條資料路徑取值，**不得另開一套查詢**（沿用 CLAUDE.md「策略引擎
  只讀已算好的序列」同一條約束，Context 組裝也不得自行重算指標）。

**降級規則**：沿用 `ai/prompt.py` 既有慣例——任何一層資料缺席（例如美股沒有月營收 YoY 概念、
新股上市不滿一季無 EPS 可比較）就整段略過，不得由 LLM 臆測數字（延續 ADR-AI-09 的精神）。

**產業鏈／輿情面**：Phase 3（產業鏈知識圖譜）與 Phase 4（新聞輿情與總經監控）目前都**尚未開發**
（只有靜態產業分類 `symbol_industry`，沒有 `industry_chain_edges` 上下游圖譜；沒有
`stock_news`／`macro_indicators` 表）。本階段**不等待**這兩個 Phase 完工，Context Schema 預留
這兩層的欄位位置，一旦 Phase 3／4 完成即可用同一套「缺席就略過」規則插入，不必回頭改 Phase 5
的架構。

**驗收標準**：
- 同一檔台股個股，Context 中可同時看到技術面／籌碼面／基本面三層數據，且基本面數值與
  `/api/v1/fundamentals/{stock_id}` 查到的值一致（同源同函式，比照 ADR-AI-09 的一致性要求）。
- 美股或月營收尚未公布的個股，基本面區塊整段消失而非顯示 `null`／`0`。
- LLM 輸出的研判理由中，若引用了基本面數字，該數字必須能在 Context 裡找到（不得臆測，比照
  現有技術面／籌碼面的行為）。

### FR-5.2　決策輸出強化

**需求描述**：
1. 新增 `target_price`（目標價）欄位，語意與現有 `stop_loss` 對稱——一個是下檔防守，一個是
   上檔滿足點；理由：現有 `resistance_levels` 是「壓力位階清單」，語意上不等於「操作目標價」，
   原始草稿五、三明確要求兩者分開。
2. 評等分級是否從現行三級（`bullish／bearish／neutral`）擴充為原始草稿要的四級（強力買進／
   分批佈局／觀望／減碼），列為待決問題 Q1，本階段先定義需求、不預先假設答案。

**相依關係**：`ai/schema.py` 的 `LLMAnalysisReport`／`AnalysisReport` 需擴充欄位；連帶
`ai_analysis_report` 資料表需新遷移（比照 `V15` 的擴充模式，不得直接改 `V14` 的既有欄位）；
前端 `AiAnalysisDialog.vue` 與 `AiReportHistory.vue` 的欄位卡片需同步顯示與可篩選。

**驗收標準**：
- 新產生的報告一律帶 `target_price`（可為 `null`，但欄位必須存在）。
- 歷史報告列表可依新增欄位（視 Q1 決議）篩選，且既有舊資料的相容處理有明確規則（例如舊評等
  值如何對應新的四級制，不可讓既有歷史報告顯示壞掉）。

---

### FR-5.3　監控清單批次／排程產生

**需求描述**：把 AI 診股從「使用者進個股頁手動點擊」擴充為對**追蹤與觀察名單**
（[api/v1/endpoints/watchlist.py](../../backend/api/v1/endpoints/watchlist.py)，見
[docs/14.追蹤個股清單優化/](../14.追蹤個股清單優化/)）批次產生，可排程執行（例如比照
[services/scheduler.py](../../backend/services/scheduler.py) 台股 14:30／美股 06:00 收盤後
排程，緊接在當日 fetch＋scan 之後）。

**相依關係與限制**：
- 沿用既有「同標的同交易日同 provider＋model 只呼叫一次」唯一鍵（ADR-AI-16／ADR-AI-21）與
  `AI_DAILY_QUOTA` 全站每日配額（規格書 §4.6）——批次觸發前必須先確認配額足夠覆蓋監控清單
  張數，否則需要獨立的批次配額上限，與手動點擊的配額分開計算，避免使用者白天點幾檔就把批次
  額度用完（或反過來，批次把配額吃光導致使用者想手動看某檔時被擋）。
- 批次執行沿用既有「先佔位、再呼叫 LLM」機制（ADR-AI-16），不需另外設計併發防重複。

**驗收標準**：
- 監控清單中的每一檔標的，在排程執行後最晚於下次登入戰情室前已有當日報告（或因配額不足而
  明確標示「本輪未產生」，不得靜默失敗）。
- 批次產生的失敗率、配額用量可在既有 `GET /api/v1/ai/usage`、`GET /api/v1/ai/status`
  查詢到，不需要另開一套統計。

### FR-5.4　戰情摘要推播整合

**需求描述**：批次產生完成後，把「當輪監控清單中評等翻多／翻空、或觸及停損／目標價的標的」
彙整成摘要，透過既有通知平台（[notify/](../../backend/notify)）推送，**不轉發整篇 Markdown
報告**——長文在 Telegram／Slack 的閱讀體驗差，這點在基礎版規格書 §13 已列為疑慮，本階段用
「摘要＋連結回戰情室」解決，而非整篇塞進訊息。

**相依關係**：比照既有事件類型的既有架構（`EventType.ALERT_SIGNAL`／`ALERT_DIGEST`／
`FETCH_COMPLETED`／`SYSTEM_HEALTH`，見 [notify/events.py](../../backend/notify/events.py)）
新增一個對稱的事件類型（例如 `AI_VERDICT_DIGEST`），比照既有 `_key_*`／`_facts_*` 一組函式與
每個 channel 各自的 Jinja 模板（`notify/templates/*.j2`），不另立一套推播機制。

**驗收標準**：
- 批次產生完成後，訂閱者在既有已設定的 channel（Slack／Telegram／Email，依規劃書
  [docs/13.通知平台/](../13.通知平台/) 的訂閱設定）收到一則摘要，內容為「N 檔翻多、M 檔翻空、
  X 檔觸及停損」等聚合資訊，附回戰情室連結，而非逐檔完整報告。
- 通知平台既有的訂閱開關、頻率上限（如有）對這個新事件類型同樣生效，不需要為 AI 摘要另開
  一套訂閱機制。

---

### FR-5.5　戰情室彙總儀表板（Vue）

**需求描述**：新增一個彙總視圖（暫名「AI 戰情室」），橫向列出監控清單中每一檔標的的：市場、
最新評等、目標價／停損價、信心度、報告產生時間、以及與規則引擎訊號的比對結果（見 FR-5.6）。
可依市場、評等、是否觸發停損／目標價篩選與排序。這是與現有「個股頁彈窗」互補的視角——個股頁
回答「這一檔現在該怎麼辦」，戰情室回答「我該優先看哪幾檔」。

**相依關係**：資料來源是 `GET /api/v1/ai/reports/latest` 的批次版本（需擴充成可一次查多檔，
避免前端對每檔各發一次請求）與 `GET /api/v1/watchlist`。UI 元件可重用
`AiAnalysisDialog.vue` 既有的評等標籤／位階卡片樣式，不必重新設計視覺語彙。

**驗收標準**：
- 開啟戰情室後，監控清單中所有標的的最新 AI 評等一次呈現，不需逐檔點擊。
- 遵守 CLAUDE.md 的兩條硬性規則：切換篩選條件不整頁重整、不重置捲動位置；同列的卡片／表格列
  高度一致。

### FR-5.6　AI 判讀與規則引擎比對

**需求描述**：當某標的當日有規則引擎（`strategies/`）觸發的訊號時，把該訊號（策略 ID、方向）
一併放進 Context（基礎版規格書 §13 已提出這個作法但未實作），並在報告與戰情室中明確標示
「AI 研判與規則訊號一致」或「AI 研判與規則訊號分歧」，讓使用者自己判斷要採信哪一邊，而不是
讓兩套系統的結論互相矛盾卻沒有任何提示。

**相依關係**：規則訊號來源為 [repositories/alert_repository.py](../../backend/repositories/alert_repository.py)
（flat-file，見 CLAUDE.md「策略/警報引擎」一節第 5 點）。**不得**讓 AI 的判斷回寫或修改
`alerts.json` 的任何內容（沿用第 3.2 節排除項目）——這是單向餵入，不是雙向同步。

**驗收標準**：
- 當某標的當日有規則引擎訊號時，該次 AI 報告的 Context 可見對應策略 ID 與方向。
- 報告與戰情室 UI 上明確顯示一致／分歧標記；規則引擎自身的輸出與行為完全不受 AI 報告影響。

## 5. 相依關係與風險

| 項目 | 說明 |
|---|---|
| Phase 3／4 尚未開發 | 產業鏈圖譜、新聞輿情與總經濾網目前只是規劃文件，沒有對應資料表與爬蟲。Phase 5 選擇不等待，先以技術＋籌碼＋基本面三層上線，架構上預留擴充點（FR-5.1） |
| 批次成本控管 | 監控清單張數 × 每日一次可能迅速逼近甚至超過現有 `AI_DAILY_QUOTA`（預設 20，規格書 §9.2）；批次上線前需重新評估配額或拆分批次／手動兩種配額 |
| 推播長文問題 | 基礎版規格書 §13 已列為風險；FR-5.4 用「摘要而非整篇」解決，但摘要的資訊取捨（哪些欄位算「重大變化」）需要另外定義規則，避免每天發送但沒人看的噪音通知 |
| 評等分級變更影響既有資料 | FR-5.2 若採四級制，既有 `bullish／bearish／neutral` 歷史資料的呈現與篩選邏輯需要相容處理，不能讓舊報告顯示錯誤或消失 |
| 兩套判斷來源可能長期矛盾 | FR-5.6 只做「標示分歧」，不做「仲裁」；長期若 AI 與規則引擎經常性矛盾，代表其中一套的品質有問題，需回頭檢視，而非由 Phase 5 直接下判斷 |

## 6. 建議開發順序

以下順序讓每一步都能獨立驗證、且後面的步驟依賴前面已驗證過的產出：

1. **FR-5.1**（三層式 Context）——純後端 Context 擴充，不動 UI，可獨立驗證數值正確性。
2. **FR-5.2**（輸出強化）——在 FR-5.1 的 Context 之上，讓 LLM 有更完整的依據判斷 `target_price`
   與（如採四級制）更細緻的評等。
3. **FR-5.3**（批次／排程）——確認配額與去重機制在批次規模下仍然成立。
4. **FR-5.6**（規則引擎比對）——批次已經穩定產生報告後，比對才有意義。
5. **FR-5.5**（戰情室 UI）——彙總視圖需要 FR-5.3／FR-5.6 的資料已經存在才有東西可呈現。
6. **FR-5.4**（推播整合）——放最後，因為「摘要要推什麼」取決於 FR-5.5 已經定義好的比對欄位。

## 7. 驗收條件總覽

- [ ] 台股個股的 AI Context 同時含技術面／籌碼面／基本面，且缺值正確降級（FR-5.1）。
- [ ] 報告輸出含 `target_price`；評等分級依 Q1 決議定案並套用（FR-5.2）。
- [ ] 監控清單可批次產生當日報告，配額用量可查詢（FR-5.3）。
- [ ] 通知平台既有 channel 收到聚合摘要，非整篇報告轉發（FR-5.4）。
- [ ] 戰情室一次呈現所有監控標的的最新評等，符合 CLAUDE.md 兩條硬性規則（FR-5.5）。
- [ ] 報告與戰情室皆標示 AI 研判與規則引擎訊號的一致／分歧，且規則引擎輸出不受影響（FR-5.6）。
